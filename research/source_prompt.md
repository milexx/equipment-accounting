Ниже приведены ВСЕ требования. Выдай структурированный документ, готовый для передачи разработчику.

## 1. Бизнес-контекст

- Есть **головное подразделение (центр)** и **много удалённых точек (регионы)**.
- Сейчас учёта оборудования нет — информация собирается вручную через Excel-файлы (много версий, ошибки, потеря данных, огромное время обработки в центре).
- Если данных мало — процесс начинается заново.

**Цель:** создать веб-приложение для централизованного учёта оборудования.

---

## 2. Функциональные требования

### Для регионов
- Видят только своё оборудование.
- Могут добавлять, редактировать, просматривать свои единицы.
- При добавлении/редактировании **обязательно прикладывают хотя бы одно фото** (до 5 фото на единицу).

### Для центра
- Видят оборудование всех регионов.
- Могут фильтровать по региону, типу оборудования, статусу, любым дополнительным полям.
- Могут редактировать любую запись.
- Могут добавлять и редактировать **типы оборудования** (какие поля собирать).

### Гибкость полей (важнейшее требование)
- Оборудование разное: ноутбуки, станки, МФУ, серверы.
- У каждого типа — свой набор полей.
- Поля должны быть гибкими: можно добавить новое поле через интерфейс, **без миграции БД и переписывания кода**.
- Регион видит только поля, нужные для выбранного типа.

---

## 3. Объём данных и производительность

- Базовая таблица оборудования — **до 500 000 записей**.
- Список с фильтрацией (2 фильтра + пагинация 50 записей) — ≤1 сек.
- Добавление/редактирование одной записи — ≤0.5 сек.
- Экспорт фильтрованного списка до 10 000 записей — ≤10 сек (или асинхронно).
- Запрещены `SELECT * FROM equipment` без `WHERE` и `LIMIT`.
- Индексы: на `region_id`, `status`, `equipment_type_id`, а также на часто фильтруемые JSONB-поля (виртуальные колонки или индексы по путям JSONB).
- Пагинация обязательна (не более 500 записей за раз без неё).

---

## 4. Работа с фотографиями (обязательно)

- От 1 до 5 фото на единицу оборудования.
- Максимальный размер одного фото — 10 МБ (на приёме).
- Хранение: **в файловой системе** (не в БД). В БД — только путь к файлу.
- Генерация миниатюр (превью) на сервере при загрузке.
- При удалении оборудования фото удаляются автоматически.
- Доступ к фото — через авторизованный эндпоинт (регион не должен видеть чужие фото).
- Общее количество файлов: до 2.5 млн. Использовать хэш-папки (например, `photos/ab/cd/uuid.jpg`).
- Логика работы с фото изолирована в отдельный сервис.

## 5. Технологический стек (обязательный)

| Слой | Технология |
|------|-------------|
| Бэкенд | Python 3.11+ / FastAPI |
| База данных | PostgreSQL 15+ (уже есть) |
| ORM и миграции | SQLAlchemy 2.0 + Alembic |
| Фронтенд | Jinja2 + HTMX + минимальный CSS |

**Обоснование стека:** новый разработчик должен понять проект за 1–2 дня.

## 6. Архитектурные заделы под корпоративные сервисы (обязательно)

### Keycloak (авторизация в будущем)
- Создать абстракцию `AuthProvider` с методами:
  - `get_current_region_id(request) -> int`
  - `has_permission(region_id, equipment_id) -> bool`
- Реализация для MVP — `DatabaseAuthProvider` (проверка по таблице).
- Реализация для Keycloak — `KeycloakAuthProvider` (JWT, атрибут с регионом).
- Смена провайдера — через переменную окружения (`AUTH_PROVIDER`).
- **Критерий:** переход на Keycloak должен затронуть не более 2 файлов.

### S3 (хранение фото в будущем)
- Создать абстракцию `PhotoStorage` с методами:
  - `save(file_data, equipment_id) -> list[str]`
  - `delete(photo_ids) -> None`
  - `get_url(photo_id) -> str`
  - `get_thumbnail_url(photo_id) -> str`
- Реализация для MVP — `FilesystemPhotoStorage` (хэш-папки).
- Реализация для S3 — `S3PhotoStorage` (корпоративный S3).
- Смена хранилища — через переменную окружения (`PHOTO_STORAGE`).
- Генерация превью — общая логика, не зависящая от хранилища.

## 7. Требования к сопровождаемости

- Код разделён на слои: `api/` (эндпоинты), `services/` (бизнес-логика), `models/` (SQLAlchemy), `schemas/` (Pydantic).
- `services/` не знают про FastAPI и HTTP.
- `api/` не знают про файловую систему и БД (только вызывают сервисы).
- Логика работы с фото изолирована в `PhotoStorage`.
- Логика аутентификации/авторизации изолирована в `AuthProvider`.
- Новый разработчик должен за 1 день понять, где добавить новый тип оборудования или новое поле.
