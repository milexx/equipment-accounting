# План MVP Модуля Мониторинга Цен

Этот документ описывает план реализации будущего post-MVP модуля "Оценщик". Он не меняет текущий MVP учёта оборудования и нужен как рабочий план для отдельного этапа разработки.

Связанный документ:

- `docs/14_price_monitoring_module.md` - ТЗ и архитектура модуля мониторинга цен.

## 1. Цель MVP Модуля

Цель MVP модуля - дать оценщику рабочий инструмент для регулярного мониторинга рыночных цен по заданным позициям оборудования.

После MVP модуля пользователь должен уметь:

- создать позицию мониторинга;
- задать поисковый запрос;
- ежедневно получать ценовой срез;
- видеть историю минимальной, максимальной и медианной цены;
- открыть объявления, на которых основан срез;
- выгрузить отчёт в CSV;
- увидеть ошибки сбора.

## 2. Правило Границ MVP

Функция входит в MVP модуля, если она нужна хотя бы для одного из обязательных сценариев:

- администратор создаёт и настраивает позицию мониторинга;
- система ежедневно собирает данные по активным позициям;
- оценщик видит динамику цен по позиции;
- оценщик может проверить объявления, на которых основан расчёт;
- администратор видит, что сбор не прошёл или источник сломался;
- данные можно выгрузить для ручного анализа.

Функция переносится после MVP модуля, если она:

- требует интеграции с текущими карточками оборудования;
- относится к ML-оценке или автоматической рекомендации цены;
- требует нескольких источников сразу;
- требует обхода технических ограничений внешних площадок;
- усложняет первый запуск без прямой пользы для ежедневного мониторинга.

## 3. Definition Of Done

MVP модуля считается готовым, когда выполнены все пункты:

- есть отдельный раздел "Оценщик";
- можно создать, отредактировать и архивировать позицию мониторинга;
- позиция содержит название, категорию, бренд, модель, поисковый запрос и лимит объявлений;
- есть источник Avito как первый адаптер или согласованный безопасный заменитель источника;
- ежедневный запуск создаёт запись запуска;
- по каждой активной позиции создаётся дневной срез;
- если объявлений нет, создаётся дневной срез со статусом `no_data`;
- найденные объявления сохраняются как ценовые наблюдения;
- ошибки сбора сохраняются в журнале;
- карточка позиции показывает график `min`, `max`, `median`;
- таблица истории совпадает с графиком;
- можно открыть объявления за выбранный день;
- CSV-экспорт работает по выбранному периоду;
- дашборд открывается быстрее 3 секунд на тестовой истории 2-3 лет;
- изменение парсера источника не требует менять отчёты и схему дневных срезов.

## 4. Риски И Ограничения

| Риск | Влияние | Решение В MVP |
|---|---|---|
| Avito ограничивает автоматический доступ | сбор может быть невозможен или нестабилен | до разработки согласовать допустимую модель доступа; предусмотреть ручной/CSV fallback после MVP |
| HTML Avito меняется | парсер ломается | вынести логику в отдельный `AvitoParser`, добавить журнал ошибок |
| Мало объявлений по редким позициям в конкретном регионе | график будет пустым | хранить `search_region`, по умолчанию использовать "Россия", писать `no_data`, показывать количество объявлений |
| Минимальная цена является выбросом | оценщик может занизить цену | показывать медиану как основной ориентир |
| Сырых объявлений станет много | отчёты могут замедлиться | графики строить по `daily_price_snapshots`, а не по `price_observations` |
| Пользователи начнут ждать автоматическую цену продажи | риск неправильного бизнес-решения | модуль только показывает рынок, цену продажи меняет человек |

## 5. Этапы Реализации

### M0. Discovery Источника Данных Avito

Статус: `todo`.

Цель: до разработки БД и интерфейса доказать, что модуль можно наполнять реальными ценовыми данными.

Задачи:

- проверить официальный портал разработчика Avito;
- выяснить, есть ли API для поиска чужих объявлений по тексту, категории и региону;
- проверить, возвращает ли API цену, ссылку, заголовок, регион и дату объявления;
- выяснить условия доступа, тарифы, лимиты и ограничения использования данных;
- если подходящего API нет, провести технический spike HTML-парсинга;
- проверить выдачу Avito по 5-10 тестовым позициям;
- проверить маппинг региона поиска Avito;
- проверить, можно ли стабильно извлекать цену, ссылку, заголовок и идентификатор объявления;
- оценить риски блокировок, CAPTCHA, изменения HTML и юридических ограничений;
- зафиксировать решение: API, HTML-парсинг или отказ от реализации модуля в текущем виде.

Критерий готовности:

- выбран технический механизм получения данных;
- подтверждено, что механизм даёт нужный минимальный набор полей;
- подтверждено, что механизм допустим для использования;
- понятны лимиты и риски;
- есть протокол discovery с примерами запросов и результатов.

Gate-решение:

- если M0 не пройден, разработку M1-M6 не начинать;
- без рабочего источника данных таблицы, дашборды и UI не имеют практического смысла.

### M1. Проектирование И Подготовка

Статус: `todo`.

Цель: после подтверждения источника данных снять оставшиеся продуктовые и организационные неопределённости.

Задачи:

- утвердить владельца процесса мониторинга;
- выбрать пилотные категории оборудования;
- закрепить результат M0 по Avito;
- утвердить выбранный механизм получения данных;
- утвердить поля позиции мониторинга;
- утвердить список статусов запуска и дневного среза;
- подготовить тестовый набор из 10-20 позиций.

Критерий готовности:

- утверждены пилотные категории;
- понятно, каким способом получать данные источника;
- есть список тестовых позиций;
- M0 пройден и риски Avito не блокируют старт разработки.

После первого запуска модуля можно развивать:

- интеграцию с карточкой оборудования;
- связь с типами оборудования;
- несколько поисковых запросов на одну позицию;
- ручной ввод дневных цен;
- Excel-экспорт;
- Telegram или email-уведомления;
- другие источники данных;
- региональные срезы;
- автоматическое исключение выбросов;
- ручное исключение объявления из расчёта;
- сравнение нескольких источников;
- рекомендованную цену продажи;
- Celery + Redis для масштабирования;
- отдельные роли и права для оценщиков;
- историю изменения поисковых запросов.

## 7. Пилотный Набор Позиций

Для первого теста рекомендуется взять 10-20 позиций из разных категорий:

- 3-5 МФУ;
- 3-5 ноутбуков;
- 2-3 сервера;
- 2-3 монитора;
- 2-3 сетевых устройства.

Критерии выбора:

- позиции реально встречаются в текущем реестре;
- по позиции есть вторичный рынок;
- название модели достаточно точное;
- есть разные уровни ликвидности: популярные и редкие позиции.

Примеры для старта:

- `Kyocera ECOSYS M2040dn`;
- `HP LaserJet Pro MFP M426`;
- `Lenovo ThinkPad T14`;
- `Dell PowerEdge R740`;
- `Dell P2419H`.

## 8. Порядок Будущей Интеграции С Учётом

Интеграцию с текущим MVP делать отдельным этапом после стабилизации оценщика.

Рекомендуемый порядок:

1. Запустить оценщик как независимый раздел.
2. Накопить 2-4 недели истории.
3. Проверить качество поисковых запросов.
4. Добавить ручную связь карточки оборудования с позицией мониторинга.
5. Показать в карточке оборудования последний рыночный диапазон.
6. Разрешить центру использовать диапазон при заполнении цены продажи.

Запрещённое поведение для первого этапа интеграции:

- автоматически менять цену продажи в карточке;
- автоматически переводить оборудование в продажу;
- скрывать от пользователя источник расчёта;
- показывать оценку без ссылки на историю и объявления.

## 10. Условия Старта Разработки

Разработку модуля стоит начинать только после выполнения условий:

- пройден M0 Discovery источника данных Avito;
- подтверждён рабочий механизм наполнения модуля реальными данными;
- утверждён владелец процесса;
- выбран пилотный набор категорий;
- согласована модель доступа к Avito;
- подтверждено, что модуль реализуется отдельно от текущего MVP;
- утверждено, что медиана является основным ориентиром;
- согласованы минимальные права доступа;
- согласованы критерии приёмки M0-M6.
