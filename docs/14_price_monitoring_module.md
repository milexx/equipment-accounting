# Модуль Мониторинга Цен

## 1. Назначение

Модуль мониторинга цен, далее "Оценщик", предназначен для регулярного отслеживания рыночных цен на оборудование, которое компания планирует оценивать, продавать или сравнивать с вторичным рынком.

Модуль проектируется как отдельный post-MVP контур. Он не меняет текущий MVP учёта оборудования и может быть подключён к карточкам оборудования позже через явную связь.

Цель модуля:

- заводить позиции оборудования для мониторинга;
- ежедневно собирать ценовые наблюдения по заданным поисковым запросам;
- хранить историю найденных объявлений;
- рассчитывать дневные минимальные, максимальные и типовые цены;
- показывать динамику цен на дашборде;
- давать оценщику проверяемую основу для решения о цене продажи.

## 2. Бизнес-Контекст

Компания владеет оборудованием, которое может быть продано на вторичном рынке. Для принятия решения о цене продажи нужно понимать рыночный диапазон по аналогичным позициям.

Сейчас анализ выполняется вручную:

- нет регулярного сбора данных;
- нет истории;
- нельзя быстро увидеть тренд;
- сложно проверить, на каких объявлениях основана оценка;
- результат зависит от конкретного сотрудника и момента проверки.

Оценщик должен превратить ручной поиск в повторяемый процесс: по каждой позиции система ежедневно фиксирует рыночные наблюдения и сохраняет дневной срез.

## 3. Границы MVP Модуля

Входит в первый MVP модуля:

- справочник отслеживаемых позиций;
- ручное создание и редактирование поискового запроса;
- архивирование позиции без удаления истории;
- один основной источник данных: Avito;
- ежедневный автоматический запуск сбора;
- ручной запуск сбора администратором;
- хранение найденных объявлений;
- дневной агрегат по позиции: минимум, максимум, средняя, медиана, количество объявлений;
- запись дня со статусом "нет данных", если объявления не найдены;
- журнал запусков и ошибок;
- дашборд по позиции;
- таблица дневной истории;
- экспорт отчёта в CSV.

Не входит в первый MVP модуля:

- изменение текущего MVP учёта оборудования;
- автоматическое сопоставление всех карточек оборудования с рыночными позициями;
- ML-оценка справедливой цены;
- сложное удаление дублей между разными площадками;
- real-time мониторинг;
- обход антибот-защит, CAPTCHA, авторизации или технических запретов площадок;
- массовая переоценка реестра оборудования.

## 4. Роли И Права

### Оценщик

Может:

- смотреть список позиций;
- смотреть дашборды;
- открывать историю цен;
- выгружать отчёты;
- просматривать найденные объявления.

### Администратор Оценщика

Может:

- создавать и редактировать позиции мониторинга;
- архивировать позиции;
- запускать сбор вручную;
- смотреть журнал запусков;
- смотреть журнал ошибок;
- включать и выключать источники данных.

### Центр

На первом этапе центр использует модуль только для просмотра отчётов. Позже центр может открывать данные оценщика из карточки оборудования.

## 5. Основные Сущности

### Категория Мониторинга

Группирует позиции для фильтрации и отчётности.

Примеры:

- ноутбуки;
- серверы;
- МФУ;
- мониторы;
- сетевое оборудование;
- складская техника.

### Позиция Мониторинга

Сущность, по которой система собирает цены.

Поля:

- название;
- категория;
- бренд;
- модель;
- ключевые характеристики;
- поисковый запрос;
- регион поиска;
- лимит объявлений за запуск;
- активность;
- дата архивирования.

Ключевой принцип: позиция мониторинга не обязана быть одной физической единицей оборудования. Это может быть рыночный шаблон, например "Kyocera ECOSYS M2040dn".

### Источник Данных

Площадка, с которой собираются цены.

Первый источник:

- Avito.

Будущие источники:

- Drom;
- OLX;
- профильные отраслевые площадки;
- ручной импорт CSV.

### Запуск Сбора

Факт выполнения мониторинга.

Фиксирует:

- источник;
- время начала и завершения;
- статус;
- количество обработанных позиций;
- количество успешных позиций;
- количество ошибок;
- общую ошибку запуска, если она была.

### Ценовое Наблюдение

Сырое найденное объявление.

Фиксирует:

- позицию;
- источник;
- запуск;
- дату сбора;
- цену;
- валюту;
- заголовок объявления;
- ссылку;
- внешний идентификатор объявления, если доступен;
- дату объявления, если доступна;
- город или регион;
- технические признаки качества.

### Дневной Срез Цен

Агрегированная запись за день по позиции и источнику.

Фиксирует:

- дату;
- минимум;
- максимум;
- среднюю;
- медиану;
- количество объявлений;
- статус дня: данные есть, данных нет, сбор не удался.

### Ошибка Парсинга

Отдельная запись о проблеме источника или позиции.

Примеры:

- источник вернул HTTP 403;
- источник вернул HTTP 429;
- изменилась структура страницы;
- цена не распознана;
- таймаут;
- пустой результат.

## 7. Архитектура Приложения

Модуль должен использовать существующий стек проекта:

- Python;
- FastAPI;
- PostgreSQL;
- SQLAlchemy;
- Alembic;
- Jinja2;
- server-rendered UI;
- опционально HTMX для частичных обновлений;
- Chart.js или аналогичный лёгкий инструмент для графиков.

Высокоуровневая структура:

```text

        |
Service layer
        |

        |
PostgreSQL
```

Контур сбора цен:

```text
APScheduler
        |
PriceMonitoringService
        |
ParserRegistry
        |

        |

```

### Слой Маршрутов

Отвечает за:

- HTML-страницы;
- обработку форм;
- экспорт CSV;
- ручной запуск сбора;
- проверку прав.

### Сервисный Слой

Отвечает за:

- создание и редактирование позиций;
- запуск мониторинга;
- расчёт дневных агрегатов;
- обработку ошибок;
- подготовку данных для графиков.

### Репозитории

Отвечают за:

- запросы к позициям;
- сохранение наблюдений;
- сохранение дневных срезов;
- выборку истории;
- выборку журналов запусков.

### Парсеры

Каждый источник реализуется отдельным адаптером.

Базовый контракт:

```text
PriceParser.fetch_prices(search_query, region, limit) -> list[PriceListing]
```

`PriceListing`:

```text
title
url
external_id
price
currency
location
listing_date
raw_payload
```

Ключевое архитектурное требование: логика Avito не должна попадать в отчёты, модели UI или бизнес-сервисы. При изменении структуры Avito должен меняться только `AvitoParser`.

## 8. Сценарии Работы

### Создание Позиции

1. Администратор открывает раздел "Оценщик".
2. Переходит в "Позиции".
3. Нажимает "Добавить позицию".
4. Заполняет название, категорию, бренд, модель.
5. Указывает поисковый запрос.
6. Указывает регион поиска и лимит объявлений.
7. Сохраняет позицию.

### Ежедневный Автоматический Сбор

1. В заданное время, например в 09:00, APScheduler создаёт запуск.
2. Сервис выбирает активные позиции.
3. Для каждой позиции вызывает парсер активного источника.
4. Сохраняет найденные объявления.
5. Рассчитывает дневной срез.
6. Если объявлений нет, пишет `no_data`.
7. Если сбор по позиции упал, пишет `failed` и ошибку.
8. После завершения обновляет статус запуска.

### Ручной Запуск Сбора

1. Администратор открывает карточку позиции.
2. Нажимает "Запустить сбор".
3. Система создаёт отдельный запуск.
4. Результат отображается в журнале.

Ручной запуск нужен для проверки новых поисковых запросов и диагностики после изменения парсера.

### Анализ Динамики

1. Оценщик открывает дашборд.
2. Выбирает позицию и период.
3. Система показывает график `min`, `max`, `median`.
4. Ниже отображается таблица дневных срезов.
5. При выборе дня открывается список объявлений, на которых основан расчёт.
6. Оценщик выгружает отчёт при необходимости.

## 11. Расчёт Показателей

Для каждого дня и позиции система считает:

- `min_price` - минимальная распознанная цена;
- `max_price` - максимальная распознанная цена;
- `avg_price` - средняя цена;
- `median_price` - медиана;
- `listing_count` - количество объявлений, вошедших в расчёт.

Рекомендация: в интерфейсе основной ориентир давать не только по min/max, но и по медиане. Минимальная цена часто может быть выбросом: некомплект, неисправное состояние, неверная категория или срочная продажа.

На первом этапе выбросы не удаляются автоматически, но помечаются флагами качества:

- подозрительно низкая цена;
- подозрительно высокая цена;
- цена не распознана;
- возможный дубль.

## 12. Нефункциональные Требования

### Производительность

Планируемая нагрузка:

- 100-200 активных позиций;
- до 50-100 объявлений на позицию в день;
- хранение истории 2-3 года.

Ожидаемый объём:

- дневные срезы: до нескольких сотен тысяч строк;
- сырые объявления: до нескольких миллионов строк при верхнем лимите.

Для MVP это допустимо для PostgreSQL без отдельного хранилища аналитики.

### Скорость Интерфейса

Требования:

- дашборд открывается быстрее 3 секунд;
- список позиций открывается быстрее 2 секунд;
- экспорт ограничивается периодом и фильтрами;
- тяжёлые графики строятся по дневным агрегатам, а не по сырым объявлениям.

### Надёжность

Требования:

- ошибка по одной позиции не останавливает весь запуск;
- ошибка источника фиксируется в журнале;
- при отсутствии объявлений создаётся запись `no_data`;
- повторный запуск за день не должен ломать историю;
- дневной срез должен быть пересчитываемым.

### Наблюдаемость

Нужно логировать:

- начало и конец запуска;
- число обработанных позиций;
- HTTP-ошибки источника;
- ошибки разбора HTML;
- длительность запроса;
- превышение лимитов;
- дни без данных.

## 13. Ограничения И Правила Работы С Avito

Avito рассматривается как внешний источник с нестабильной HTML-структурой и собственными правилами доступа. Перед промышленной реализацией необходимо отдельно проверить актуальные правила площадки, `robots.txt`, доступность официального или партнёрского API и юридические ограничения.

Технические требования к реализации:

- проверять правила доступа перед включением парсинга;
- не обходить CAPTCHA, авторизацию, rate limits и технические блокировки;
- не использовать прокси как способ обхода запрета площадки;
- использовать малые лимиты выборки;
- задавать задержку между запросами;
- явно идентифицировать user-agent сервиса;
- сохранять HTTP-статусы `403`, `429`, `5xx`;
- автоматически выключать источник или переводить запуск в `failed`, если блокировки стали массовыми;
- уведомлять администратора о повторяющихся сбоях.

Если будет доступен официальный API или партнёрский доступ, он должен быть предпочтительным вариантом по сравнению с HTML-парсингом.

## 14. Расширяемость

### Добавление Нового Источника

Для нового источника нужно:

1. Добавить запись в `market_sources`.
2. Реализовать новый класс парсера.
3. Зарегистрировать его в `ParserRegistry`.
4. Добавить настройки лимитов.
5. Проверить дневной сбор и отчёты.

Отчёты и дневные срезы не должны зависеть от конкретной площадки.

### Масштабирование

Если позиций станет больше 500 или источников станет несколько, нужно рассмотреть переход:

- с APScheduler на Celery;
- с синхронного сбора на очередь задач;
- с одного процесса на пул worker-процессов;
- с простой таблицы ошибок на полноценный мониторинг задач.

Для первого MVP модуля APScheduler достаточен.

## 15. Интеграция С Текущим Учётом

На первом этапе интеграция с карточками оборудования не требуется.

Будущая связь:

```text
equipment.price_monitoring_item_id -> monitored_items.id
```

Возможный сценарий:

1. Центр открывает карточку оборудования.
2. Видит блок "Рыночная цена".
3. Выбирает или создаёт позицию мониторинга.
4. Система показывает последний диапазон цен и тренд.
5. Центр использует эти данные при заполнении цены продажи.

Важно: модуль оценщика не должен автоматически менять цену продажи в карточке оборудования без явного действия пользователя.

## 17. Критерии Приёмки

Модуль считается готовым, если:

- можно создать и архивировать позицию мониторинга;
- можно задать поисковый запрос;
- ежедневный запуск создаёт дневную запись по каждой активной позиции;
- при отсутствии объявлений создаётся `no_data`;
- сырые объявления сохраняются со ссылкой и ценой;
- график показывает минимум, максимум и медиану за выбранный период;
- таблица истории соответствует графику;
- отчёт выгружается в CSV;
- ошибки источника видны администратору;
- изменение парсера Avito не требует менять отчёты и БД;
- дашборд открывается быстрее 3 секунд на истории 2-3 лет.

## 18. Предварительные Проектные Решения

Этот раздел фиксирует рабочие решения для дальнейшей детализации модуля. Решения не меняют текущий MVP учёта оборудования.

### География И Регион Поиска

В первом MVP модуля позиция мониторинга хранит регион поиска для внешней площадки. В контексте Avito это географический фильтр поиска объявлений на Avito, а не регион пользователя системы и не регион владения оборудованием.

Решения:

- у позиции есть поле `search_region`;
- значение по умолчанию - "Россия";
- "Россия" означает общий рыночный диапазон без ограничения одним городом или регионом, если площадка поддерживает такой режим;
- если указан конкретный регион, адаптер источника должен преобразовать его в поддерживаемый площадкой параметр или URL поиска;
- если регион не поддерживается или не сопоставляется однозначно, система должна показать ошибку настройки позиции;
- отчёт первого MVP строится по одному региону позиции, без сравнения регионов между собой;
- региональные сравнения переносятся на следующий этап.

Причины:

- для оборудования вторичного рынка локальная ликвидность может быть низкой;
- федеральный поиск быстрее даёт достаточную выборку;
- меньше риск получить пустые дни по редким позициям;
- регион нужно хранить сразу, чтобы позже добавить региональные срезы без изменения смысла позиции мониторинга.

### Состояние Оборудования

В первом MVP модуля состояние учитывается как фильтр качества, но не как обязательный строгий классификатор.

Базовые значения:

- `any` - любое состояние;
- `working` - рабочее;
- `not_working` - неисправное;
- `for_parts` - на запчасти;
- `new` - новое.

На первом этапе состояние задаётся в позиции мониторинга как ожидаемое состояние и используется оценщиком при ручной проверке объявлений. Автоматически определять состояние по тексту объявления можно позже.

### Основной Ценовой Ориентир

В отчётах показываются минимум, максимум, средняя и медиана.

Основной ориентир для принятия решения - медиана, а не минимальная цена.

Причины:

- минимальная цена часто является выбросом;
- максимальная цена часто отражает завышенное ожидание продавца;
- медиана устойчивее к некомплекту, срочным продажам и ошибочным категориям.

Минимум и максимум сохраняются, потому что они нужны для понимания рыночного диапазона.

### Обработка Подозрительных Объявлений

В первом MVP модуль не удаляет подозрительные объявления автоматически.

Система должна помечать объявления флагами:

- цена ниже медианы более чем на заданный процент;
- цена выше медианы более чем на заданный процент;
- цена не распознана;
- нет ссылки;
- возможный дубль.

Исключение из расчёта можно добавить позже как настройку позиции или отчёта. Для первого этапа важнее сохранить проверяемость данных.

### Несколько Поисковых Запросов

В первом MVP у позиции один основной поисковый запрос.

Задел на будущее: добавить таблицу `monitored_item_queries`, если потребуется несколько запросов на одну позицию.

Пример будущего использования:

- основной запрос: `Kyocera ECOSYS M2040dn`;
- альтернативный запрос: `Kyocera M2040dn`;
- запрос с русским описанием: `МФУ Kyocera 2040`.

Для первого этапа один запрос проще контролировать и отлаживать.

### Хранение HTML

В первом MVP не хранить полный HTML страниц объявлений.

Допустимо хранить:

- нормализованные поля объявления;
- внешний идентификатор;
- ссылку;
- небольшой `raw_payload_json` с техническими данными парсера;
- HTML-фрагмент карточки только в debug-режиме и только ограниченное время.

Причины:

- полный HTML увеличивает объём хранения;
- может содержать лишние персональные или технические данные;
- для отчётности достаточно нормализованных полей и ссылки.

### Уведомления О Сбоях

В первом MVP достаточно журнала ошибок в интерфейсе.

Минимальное уведомление:

- блок "Ошибки за последние 24 часа" на главной странице оценщика;
- статус источника в списке запусков;
- отдельная страница `/pricing/errors`.

Telegram или email-уведомления оставить как следующий этап. Их стоит добавлять после накопления первых реальных сбоев, чтобы не создавать шум.

### Экспорт

В первом MVP достаточно CSV.

Excel-экспорт можно добавить позже, если пользователи действительно будут готовить отчёты в `.xlsx` с форматированием.

CSV должен содержать:

- позицию;
- категорию;
- бренд;
- модель;
- дату;
- минимум;
- максимум;
- среднюю;
- медиану;
- количество объявлений;
- статус дня.

### Связь С Текущими Типами Оборудования

В первом MVP модуль оценщика не связывается жёстко с текущими типами оборудования из admin-раздела.

Причина: позиция мониторинга - это рыночная сущность, а тип оборудования в текущем MVP - операционная классификация карточки.

Задел на будущее:

```text
monitored_items.equipment_type_id -> equipment_types.id
equipment.price_monitoring_item_id -> monitored_items.id
```

Связь добавляется только после того, как будет понятно, как центр реально использует оценочные позиции.

### Модель Доступа К Avito

До реализации нужно выбрать юридически допустимый способ доступа.

Предпочтительный порядок:

1. официальный или партнёрский API, если он доступен и покрывает поиск рыночных объявлений;
2. HTML-парсинг Avito, если открытого API для такого поиска нет и парсинг допустим;
3. ручной или CSV-импорт только как временный fallback, но не как целевой механизм.

Не закладывать в архитектуру обход CAPTCHA, блокировок, авторизации или ограничений площадки.

Решение по источнику является gate-условием проекта. Если нет подтверждённого механизма получения цен с Avito, разработку БД, UI и дашбордов не начинать. Сначала проводится discovery: API, условия доступа, технический spike парсинга, проверка 5-10 тестовых позиций и фиксация минимального набора данных.

### Ручной Ввод Цен

Ручной ввод цен нужен как fallback, но не входит в первый технический MVP.

Рекомендуемый post-MVP сценарий:

- оценщик вручную добавляет дневной срез;
- источник помечается как `manual`;
- запись отделяется от автоматического сбора;
- в отчётах видно, какие точки внесены вручную.
