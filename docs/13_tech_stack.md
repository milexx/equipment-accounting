# Техстек Системы

## 1. Назначение Стека

Система построена как серверное веб-приложение для внутреннего учёта оборудования. Главные требования к стеку:

- быстрый запуск MVP;
- простая поддержка без сложного frontend-build;
- PostgreSQL как основное хранилище;
- гибкие поля оборудования;
- серверный HTML-интерфейс;
- возможность позже заменить MVP-решения на промышленные интеграции.

## 2. Backend

### FastAPI

Используется как основной web-framework.

Задачи:

- HTTP-маршруты;
- обработка форм;
- HTML-ответы через Jinja2;
- healthcheck `/health`;
- разделение API по модулям: `auth`, `equipment`, `region`, `admin`, `documentation`.

Почему выбран:

- быстрый и понятный для MVP;
- хорошо работает с dependency injection;
- удобно совмещает HTML-страницы и будущие JSON API.

### Uvicorn

ASGI-сервер для локального и demo-запуска.

Команда запуска:

```bash
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8010
```

## 3. База Данных

### PostgreSQL

Основная база данных системы.

Используется для:

- регионов;
- пользователей;
- типов оборудования;
- динамических полей;
- карточек оборудования;
- фото;
- audit log;
- статусов и маршрутов обработки.

Текущая локальная база:

```text
equipment_accounting_dev
```

### SQLAlchemy

ORM и слой работы с БД.

Используется для:

- моделей таблиц;
- связей между сущностями;
- транзакций;
- блокировок `with_for_update`;
- запросов реестра и фильтров.

### Alembic

Миграции схемы БД.

Команда применения миграций:

```bash
.venv/bin/alembic upgrade head
```

## 4. Frontend

### Jinja2

Основной шаблонизатор HTML.

Используется для страниц:

- `/`;
- `/login`;
- `/region`;
- `/equipment`;
- `/equipment/new`;
- `/equipment/{id}`;
- `/admin`;
- `/documentation`.

Почему выбран:

- не нужен отдельный frontend-build;
- удобно для MVP и внутренней системы;
- проще поддерживать формы, таблицы и серверные проверки.

### Server-rendered UI

Интерфейс рендерится на сервере.

Это означает:

- формы отправляются обычными POST/GET-запросами;
- после действий чаще всего используется redirect;
- данные проверяются на backend;
- UI проще отлаживать и разворачивать.

### HTMX-ready Подход

В MVP HTMX не является обязательной зависимостью интерфейса, но архитектура допускает постепенное добавление интерактивных фрагментов без перехода на SPA.

Потенциальные будущие места для HTMX:

- обновление очередей центра;
- inline-редактирование справочников;
- drawer карточки оборудования;
- частичная перерисовка таблиц после фильтрации.

## 5. Фото И Файлы

### Pillow

Используется для обработки изображений:

- проверка корректности изображения;
- чтение размеров;
- исправление EXIF-ориентации;
- создание thumbnail.

### Файловое Хранилище

В MVP фото хранятся на файловой системе.

Путь задаётся через:

```text
PHOTO_ROOT
```

Текущий demo-путь:

```text
./var/photos
```

Публичная раздача:

```text
/media/photos
```

Post-MVP замена:

- S3-compatible хранилище;
- авторизованная раздача файлов;
- отдельная политика хранения оригиналов и thumbnails.

## 6. Авторизация

### MVP Auth Provider

В MVP используется локальный `AuthProvider`.

Режимы:

- `database`;
- `demo`;
- `keycloak` зарезервирован, но не реализован.

Роли:

- `region`;
- `center`;
- `center_admin`.

Demo/database режим поддерживает выбор пользователя через:

- `/login`;
- cookie `demo_user`;
- query-параметр `?as=...`;
- заголовок `x-demo-user`.

Post-MVP замена:

- Keycloak;
- SSO;
- реальные группы и роли;
- полноценные сессии и logout-политика.

## 7. Динамические Поля

Динамические поля оборудования реализованы через:

- таблицу `equipment_type_fields`;
- JSONB-поле `equipment.attributes`.

Это позволяет:

- добавлять поля через admin UI;
- включать и отключать поля;
- настраивать обязательность;
- делать поля фильтруемыми;
- не менять схему БД при каждом новом типе оборудования.

Ограничение MVP:

- сложные валидации и зависимости между полями не реализованы;
- индексирование отдельных JSONB-полей можно добавить после появления реальных данных и частых фильтров.

## 8. Конкурентная Работа

Для защиты от параллельного перетирания данных используется:

- поле `equipment.row_version`;
- проверка версии при сохранении;
- транзакции;
- `SELECT ... FOR UPDATE` в критичных действиях.

Сценарии:

- центр и регион не должны незаметно перезаписать изменения друг друга;
- повторная отправка формы не должна создавать дубли;
- массовое создание карточек не должно блокировать работу центра со списком.

## 9. Audit Log

Таблица:

```text
equipment_audit_log
```

В MVP пишутся события:

- изменение карточки;
- действия центра;
- бизнес-маршруты продажи/списания;
- операции с фото.

Post-MVP расширение:

- audit admin-изменений;
- audit экспорта;
- фильтры и отдельный экран истории;
- хранение actor/context для промышленных интеграций.

## 10. Конфигурация

Настройки читаются через `pydantic-settings` из `.env`.

Основные переменные:

```text
DATABASE_URL
AUTH_PROVIDER
PHOTO_STORAGE
PHOTO_ROOT
MAX_PHOTO_SIZE_MB
EXPORT_SYNC_LIMIT
SESSION_SECRET
```

Пример находится в:

```text
.env.example
```

## 11. Проверки Качества

Технические проверки:

```bash
.venv/bin/python -m compileall app scripts
.venv/bin/ruff check app scripts
```

MVP-приёмка:

```bash
.venv/bin/python -c "from scripts.check_mvp_acceptance import main; raise SystemExit(main())"
```

Проверка проходит:

- smoke основных страниц;
- доступы ролей;
- защиту от двойной отправки;
- конфликт `row_version`;
- загрузку/удаление фото;
- 60 параллельных созданий карточек;
- работу центра со списком во время массового создания.

## 12. Осознанно Не В MVP

Не входит в текущий MVP:

- SPA на React/Vue;
- Keycloak/SSO;
- S3;
- фоновые очереди;
- асинхронные экспорты;
- полнотекстовый поиск;
- BI/dashboard-аналитика;
- мобильное приложение;
- QR/barcode-сканирование;
- интеграция с ITSM/RMM/CMDB.

Эти пункты относятся к backlog после MVP и должны оцениваться отдельно.
