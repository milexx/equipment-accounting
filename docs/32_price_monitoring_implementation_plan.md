## 1. Цель

Реализовать отдельный модуль "Оценщик", который позволяет центру вести позиции мониторинга, ежедневно собирать рыночные объявления, сохранять дневные ценовые срезы и смотреть историю min/max/median.

Первый релиз не должен менять текущие сценарии учёта оборудования:

- `/region`;
- `/equipment`;
- статусы оборудования;
- текущую цену продажи;
- карточку оборудования как обязательную точку входа.

Модуль добавляется отдельным контуром `/pricing`.

## 2. Главный Gate Перед Разработкой

Перед подключением модуля к основному приложению нужно пройти endurance test источника Avito.

Текущий статус источника:

```text
pipeline_works_http_unstable
```

Что уже подтверждено:

- clean-room worker умеет извлекать объявления из live HTML;
- нормализация в JSON работает;
- фильтр делит объявления на `relevant`, `unknown`, `rejected`;
- дневной snapshot считается по `relevant`.

Что ещё не подтверждено:

- стабильный live HTTP-доступ;
- работа по нескольким позициям;
- 3-5 дневная повторяемость;
- качество фильтра по разным категориям.

Gate-решения после endurance test:

| Решение | Когда принимать | Что делать |
|---|---|---|
| `go_worker_prototype` | 3-5 дней дают данные без постоянных блокировок | переносить worker в приложение как экспериментальный источник |
| `hold_http_unstable` | источник часто получает `403`, `429`, CAPTCHA или пустой HTML | не писать production-интеграцию, оставить модуль в research |
| `browser_profile_research` | простой HTTP нестабилен, но бизнес хочет продолжать | отдельно исследовать браузерный профиль без обхода CAPTCHA и proxy rotation |

До gate-решения нельзя начинать миграции и UI основного модуля, кроме подготовки документации и изолированного research.

## 3. Этап A. Подготовить Endurance Test

Цель: аккуратно проверить реальную пригодность источника без частых запросов.

Ограничение:

```text
Не делать live-запросы к Avito чаще одного раза в день.
```

Задачи:

1. Расширить `research/avito-monitor-worker-poc/config/search_jobs.example.json` до 3 тестовых позиций.
2. Подготовить локальный `config/search_jobs.json`, не коммитить его.
3. Выбрать позиции:
   - `Kyocera ECOSYS M2040dn`;
   - `Lenovo ThinkPad T14`;
   - `Dell PowerEdge R740`.
4. Для каждой позиции задать:
   - `code`;
   - `position_name`;
   - `search_url`;
   - `required_terms`;
   - `negative_terms`;
   - `price_min`;
   - `price_max`.
5. Добавить в README POC таблицу endurance-журнала.
6. Запустить один live run.
7. Зафиксировать результат в отдельном документе `docs/33_price_monitoring_endurance_day_1.md`.

Критерий готовности:

- есть конфиг на 3 позиции;
- один run выполнен без повторных запросов;
- по каждой позиции есть статус `success`, `blocked`, `captcha`, `no_data` или `parser_error`;
- сырые результаты сохранены только в ignored `runs/`;
- в git попадает только отчёт, не HTML и не данные объявлений.

## 4. Этап B. Endurance Test 3-5 Дней

Цель: понять, можно ли использовать HTTP worker как основу первого прототипа.

Режим:

- 3 позиции;
- 1 запуск в день;
- 3-5 дней;
- без cookies;
- без proxy;
- без CAPTCHA bypass;
- без частых повторов при ошибке.

Каждый день фиксировать:

- дату и время запуска;
- статус по каждой позиции;
- HTTP status;
- количество raw listings;
- количество normalized;
- количество relevant;
- количество unknown;
- количество rejected;
- min/max/median;
- замечания по фильтру.

Критерий `go_worker_prototype`:

- минимум 3 последовательных дня без постоянного `403`, `429` или CAPTCHA;
- хотя бы 2 из 3 позиций дают пригодные данные;
- parser не ломается на структуре HTML;
- фильтр не пропускает очевидный мусор в min price без пометки `unknown` или `rejected`.

Критерий `hold_http_unstable`:

- блокировки повторяются чаще успешных запусков;
- HTML не содержит нужного embedded state;
- результаты непредсказуемы и не подходят для дневной истории.

## 5. Этап C. Backend-Скелет Модуля

Начинать только после `go_worker_prototype`.

Цель: добавить модели данных и backend-сервисы без UI-сложности.

Задачи:

1. Создать модели в `app/models/pricing.py`.
2. Создать Alembic-миграцию.
3. Добавить таблицы:
   - `price_categories`;
   - `monitored_items`;
   - `market_sources`;
   - `price_scrape_runs`;
   - `price_observations`;
   - `daily_price_snapshots`;
   - `parser_errors`.
4. Добавить seed для источника `avito`.
5. Добавить repository/service слой:
   - создание позиции;
   - обновление позиции;
   - архивирование позиции;
   - сохранение наблюдений;
   - пересчёт дневного среза.
6. Покрыть сервис snapshot минимальными тестами или acceptance script.

Критерий готовности:

- миграция применяется на dev-БД;
- дневной snapshot можно посчитать из набора наблюдений;
- повторный пересчёт за тот же день обновляет одну запись, а не плодит дубли;
- `no_data` сохраняется явно.

## 6. Этап D. Перенос Worker В Приложение

Цель: превратить research worker в внутренний adapter без привязки UI к Avito.

Задачи:

1. Создать:
   - `app/services/pricing_parsers/base.py`;
   - `app/services/pricing_parsers/registry.py`;
   - `app/services/pricing_parsers/avito.py`.
2. Описать контракт `PriceParser`.
3. Перенести только clean-room код из research POC.
4. Оставить Avito-специфику внутри adapter.
5. Добавить stop-on-block:
   - `403`;
   - `429`;
   - CAPTCHA text;
   - access restricted text.
6. Сохранять ошибки в `parser_errors`.
7. Сохранять raw HTML только в runtime-директорию, не в git.
8. Добавить задержки между позициями.

Критерий готовности:

- ручной backend-запуск одной позиции создаёт `price_scrape_run`;
- объявления сохраняются как `price_observations`;
- дневной срез создаётся после запуска;
- при блокировке источник не делает retry loop.

## 7. Этап E. UI `/pricing`

Цель: дать центру и администратору рабочий интерфейс без связи с карточками оборудования.

Маршруты:

- `GET /pricing` - список позиций;
- `GET /pricing/items/new` - форма создания;
- `POST /pricing/items` - создание;
- `GET /pricing/items/{id}` - карточка позиции;
- `GET /pricing/items/{id}/edit` - форма редактирования;
- `POST /pricing/items/{id}` - сохранение;
- `POST /pricing/items/{id}/archive` - архивирование;
- `POST /pricing/items/{id}/run` - ручной запуск одной позиции;
- `GET /pricing/runs` - журнал запусков;
- `GET /pricing/runs/{id}` - детали запуска;
- `GET /pricing/items/{id}/export.csv` - CSV-экспорт истории.

Права:

- `center_admin` - управление позициями и ручной запуск;
- `center` - просмотр дашбордов и экспорт;
- `region` - нет доступа в первом релизе.

Критерий готовности:

- позицию можно создать из UI;
- позицию можно отключить без удаления истории;
- карточка показывает историю срезов;
- можно открыть объявления выбранного дня;
- журнал запусков показывает ошибки.

## 8. Этап F. Графики И Экспорт

Цель: сделать модуль полезным оценщику.

Задачи:

1. Добавить график min/max/median по дням.
2. Использовать локальный Chart.js или простую HTML-таблицу на первом шаге.
3. Добавить фильтр периода.
4. Добавить таблицу daily snapshots.
5. Добавить просмотр объявлений за день.
6. Добавить CSV:
   - дневные срезы;
   - объявления по выбранному периоду.

Критерий готовности:

- график и таблица показывают одинаковые данные;
- медиана видна как основной ориентир;
- `unknown` объявления не участвуют в расчёте, но доступны для проверки;
- CSV открывается в Excel/LibreOffice.

## 9. Этап G. Scheduler

Цель: включить ежедневный сбор.

Для dev/demo допустим встроенный scheduler при одном uvicorn-процессе.

Для production желательно отдельный worker или systemd timer, чтобы не получить несколько параллельных запусков при масштабировании web-процессов.

Задачи:

1. Выбрать режим:
   - встроенный scheduler для demo;
   - отдельный command/systemd timer для production.
2. Добавить lock от параллельного запуска.
3. Настроить ежедневное окно запуска.
4. Добавить ручной запуск всех активных позиций.
5. Логировать итог `success`, `partial_failed`, `failed`.

Критерий готовности:

- ежедневный run создаётся автоматически;
- ошибка одной позиции не останавливает остальные;
- повторный запуск не стартует параллельно;
- администратор видит последний успешный запуск.

## 10. Этап H. Acceptance И Пилот

Цель: проверить модуль на данных, похожих на реальные.

Acceptance checklist:

1. Создать 10-20 monitored items.
2. Запустить ручной сбор по одной позиции.
3. Запустить ручной сбор по всем активным позициям.
4. Проверить `success`, `no_data`, `blocked`, `parser_error`.
5. Проверить дневные срезы.
6. Проверить график за период.
7. Проверить объявления за день.
8. Проверить CSV.
9. Проверить доступы:
   - `center_admin`;
   - `center`;
   - `region`.
10. Проверить, что текущие `/region` и `/equipment` не изменились.

Критерий пилотной готовности:

- 10-20 позиций работают минимум 5 дней;
- данные можно проверить по ссылкам;
- ошибки источника видны;
- оценщик может использовать медиану и диапазон как рыночный ориентир;
- система не предлагает автоматическую цену продажи.

## 11. Что Не Делать В Первом Релизе

Не включать в первый релиз:

- автоматическую оценку цены продажи;
- ML matching объявлений;
- связь каждой карточки оборудования с monitored item;
- сравнение регионов;
- несколько источников одновременно;
- покупку платных источников;
- CAPTCHA bypass;
- proxy rotation;
- phone parsing;
- автоматическую публикацию объявлений;
- изменение текущего lifecycle оборудования.

## 13. Ближайший Следующий Шаг

Следующий конкретный шаг:

```text
Подготовить endurance test на 3 позиции, но live Avito run делать только один раз и не чаще одного раза в день.
```

После первого run:

- не повторять запрос при блокировке;
- сохранить runtime-результаты в ignored `runs/`;
- в git добавить только отчёт дня;
- принять промежуточное решение: продолжать endurance или остановить источник как нестабильный.
