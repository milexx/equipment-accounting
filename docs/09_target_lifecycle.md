# Целевой Жизненный Цикл Оборудования

Этот документ уточняет бизнес-смысл системы.

Система создаётся не для полного учёта всего имущества организации, а для работы с оборудованием, которое стало неиспользуемым и должно пройти дальнейшую судьбу:

```text
Неиспользуемое оборудование
        |
        v
Описание и подтверждение состояния
        |
        +--> Нерабочее -> дефектовка -> списание -> утилизация
        |
        +--> Рабочее -> оценка -> подготовка к продаже -> продажа / магазин
```

## 1. Текущая Потребность

Первая версия системы должна закрыть текущую потребность:

- регионы заводят неиспользуемое оборудование;
- прикладывают фото;
- указывают состояние;
- центр проверяет качество данных;
- центр принимает решение, что делать с оборудованием дальше.

## 2. Состояние Оборудования

После первичного ввода оборудование классифицируется по состоянию:

- `unknown` - состояние ещё не подтверждено;
- `working` - рабочее;
- `broken` - нерабочее;
- `partially_working` - частично рабочее;
- `requires_diagnostics` - требуется диагностика.

Для MVP достаточно поддержать:

- `working`;
- `broken`;
- `requires_diagnostics`.

## 3. Нерабочее Оборудование

Для нерабочего оборудования обязательно:

- описание поломки;
- фото, подтверждающие поломку;
- комментарий региона;
- решение центра.

Примеры поломок:

- не включается;
- повреждён корпус;
- отсутствуют комплектующие;
- разбит экран;
- неисправен блок питания;
- следы залития;
- не проходит диагностику.

Нерабочее оборудование идёт в процесс:

```text
broken -> writeoff_review -> writeoff_approved -> disposal_pending -> disposed
```

## 4. Рабочее Оборудование

Рабочее оборудование идёт в процесс оценки и продажи:

```text
working -> valuation_pending -> valued -> sale_ready -> listed_for_sale -> sold
```

Для рабочего оборудования нужно хранить:

- комплектность;
- внешний вид;
- состояние;
- рыночную/оценочную стоимость;
- рекомендованную цену продажи;
- решение центра о продаже;
- статус публикации в будущем магазине.

## 5. Магазин Оборудования

Магазин не входит в первый MVP, но архитектурно должен быть предусмотрен.

Будущий магазин:

- показывает только оборудование со статусом `listed_for_sale`;
- скрывает внутренние служебные поля;
- показывает карточку с фото, описанием, состоянием и ценой;
- позволяет оставить заявку/интерес к покупке;
- может быть доступен ограниченному кругу пользователей.

В MVP нужно предусмотреть поля:

- `sale_price`;
- `valuation_amount`;
- `sale_status`;
- `is_public_listing`;
- `sale_description`.

## 6. Решение Центра

Центр должен иметь отдельное действие после проверки:

- отправить на доработку;
- принять как рабочее;
- принять как нерабочее;
- отправить на диагностику;
- отправить на оценку;
- отправить на списание;
- подготовить к продаже.

## 7. Фото Как Доказательство

Фото перестают быть просто иллюстрацией. Они становятся подтверждением состояния.

Нужно поддержать типы фото:

- `general` - общий вид;
- `serial` - серийный/инвентарный номер;
- `defect` - поломка/дефект;
- `completeness` - комплектность;
- `other` - прочее.

Для нерабочего оборудования минимум одно фото должно иметь тип `defect`.
