# План Реализации MVP

Этот документ - контрольная точка разработки. По нему должно быть понятно:

- что входит в MVP;
- что уже сделано;
- что осталось до завершения;
- какие новые идеи добавлять в MVP, а какие переносить в backlog после MVP.

## 1. Правило Границ MVP

Идея или доработка входит в MVP, если она нужна хотя бы для одного из обязательных сценариев:

- регион заводит неиспользуемое оборудование и отправляет его в центр;
- регион исправляет карточку после возврата на доработку;
- центр видит общий реестр и рабочие очереди;
- центр проверяет карточку, принимает её или возвращает на доработку;
- центр направляет оборудование по базовому маршруту: диагностика, списание, оценка, продажа;
- система не теряет данные при параллельной работе регионов и центра;
- администратор центра может подготовить пользователей, регионы, типы оборудования и поля;
- из системы можно получить минимальную выгрузку для дальнейшей работы.

Идея переносится в backlog после MVP, если она:

- не блокирует ручной запуск процесса учёта;
- относится к удобству, аналитике, автоматизации или интеграциям;
- требует отдельного большого контура разработки;
- заменяет временное MVP-решение промышленной интеграцией;
- нужна только после накопления реальных данных.

## 2. Definition Of Done Для MVP

MVP считается завершённым, когда выполнены все пункты:

- регион может войти, увидеть только свой регион и создать карточку оборудования;
- регион может сохранить черновик, загрузить фото, отправить запись в центр;
- регион может исправить запись после возврата центра;
- центр может войти, видеть все регионы, фильтровать и открывать карточки;
- центр может принять запись, вернуть на доработку, отправить на диагностику, списание, оценку или продажу;
- центр/admin может управлять базовыми справочниками: регионы, пользователи, типы оборудования, поля типов;
- фото можно добавлять, назначать, удалять и менять порядок;
- основные изменения пишутся в audit log;
- конкурентное редактирование защищено через `row_version`;
- есть базовый экспорт реестра;
- демо-данные создаются одной командой;
- есть краткая инструкция запуска и приёмки;
- dev-сервер проходит smoke-проверку `/health`, `/login`, `/region`, `/equipment`, `/equipment/new`, `/equipment/{id}`.

## 3. Статусы

Используемые статусы:

- `done` - реализовано и проверено;
- `partial` - есть рабочая часть, но MVP-критерий ещё не закрыт;
- `todo` - не начато или есть только задел;
- `post-mvp` - сознательно не входит в MVP.

## 5. Очередь Работ До Завершения MVP

### M1. Admin: Пользователи И Регионы

Цель: центр может сам подготовить демо/рабочую структуру без ручного seed.

Статус: `done`.

Задачи:

- добавить admin-раздел для `center_admin`;
- список пользователей;
- создание/редактирование пользователя;
- выбор роли `region`, `center`, `center_admin`;
- привязка регионального пользователя к региону;
- блокировка/разблокировка пользователя;
- список регионов;
- создание/редактирование региона;
- включение/выключение региона;
- audit log для admin-изменений вынесен в общий audit-блок стабилизации.

Критерий готовности:

- новый регион и пользователь создаются через UI;
- региональный пользователь после входа видит только свой регион.

### M2. Admin: Типы Оборудования И Поля

Цель: центр может менять структуру карточек без разработчика.

Статус: `done`.

Задачи:

- список типов оборудования;
- создание/редактирование типа;
- включение/выключение типа;
- список полей типа;
- создание/редактирование поля;
- настройка типа поля, обязательности, порядка, подсказки;
- настройка вариантов для `select`/`multiselect`;
- выключение поля без удаления исторических данных;
- audit log для изменений типов и полей.

Критерий готовности:

- новый тип и поле создаются через UI;
- регион видит новое поле в форме создания;
- старые карточки не ломаются после выключения поля.

### M3. Реестр: Фильтры И Экспорт

Цель: центр может найти нужные записи и выгрузить реестр.

Статус: `done`.

Задачи:

- фильтр по региону;
- фильтр по типу оборудования;
- фильтр по местонахождению;
- фильтр по статусу продажи;
- минимальная поддержка фильтруемых динамических полей;
- экспорт CSV по текущим фильтрам;
- ограничение объёма экспорта;
- audit log события экспорта вынесен в общий audit-блок стабилизации.

Критерий готовности:

- центр фильтрует список по ключевым признакам;
- экспорт открывается в табличном редакторе;
- экспорт не блокирует создание и редактирование карточек.

### M4. Маршруты Списания, Оценки И Продажи

Цель: MVP закрывает полный базовый путь после принятия центром.

Статус: `done`.

Задачи:

- архивирование карточки;
- soft delete карточки;
- ввод оценочной стоимости;
- ввод цены продажи;
- описание для продажи;
- признак публикации;
- переходы `valued`, `listed_for_sale`, `sold`;
- переходы `writeoff_approved`, `disposal_pending`, `disposed`, если нужны для MVP-приёмки.

Критерий готовности:

- по рабочему оборудованию можно пройти путь до продажи;
- по нерабочему оборудованию можно пройти путь до списания/утилизации;
- все переходы отражаются в истории.

### M5. Приёмка И Стабилизация

Цель: понять, что разработка MVP закончена.

Статус: `done`.

Задачи:

- smoke-тест основных страниц;
- проверка доступа регионов;
- проверка двойной отправки формы;
- проверка конфликта `row_version`;
- проверка загрузки/удаления фото;
- проверка создания 60 параллельных карточек;
- проверка работы центра со списком во время массового создания;
- обновление `README.md`;
- инструкция для admin/оператора;
- финальное обновление `docs/continuation.md`.

Критерий готовности:

- все проверки пройдены командой приёмки;
- `README.md` и инструкция оператора/admin обновлены;
- финальное состояние зафиксировано MVP-коммитом.

## 6. Backlog После MVP

Эти идеи не блокируют завершение MVP и выполняются отдельно:

- Keycloak-интеграция;
- S3-хранилище фото;
- импорт из Excel;
- сложная аналитика и dashboards;
- полнотекстовый поиск;
- мобильное приложение;
- публичная витрина/магазин;
- асинхронные фоновые экспорты;
- уведомления по email/Telegram;
- электронное согласование списания;
- распознавание серийных номеров по фото;
- HEIC/Live Photo поддержка;
- пакетная загрузка фото;
- массовое редактирование карточек;
- SLA/метрики обработки заявок;
- продвинутые отчёты по регионам.
- расширенный audit log для admin-изменений, изменений типов/полей и экспорта.

## 7. Как Обрабатывать Новые Идеи

Когда появляется новая доработка:

1. Описать её одним предложением: какую проблему пользователя она решает.
2. Проверить по правилу границ MVP из раздела 1.
3. Если без неё нельзя завершить один из обязательных сценариев, добавить её в соответствующий блок M1-M5.
4. Если она улучшает продукт, но не блокирует запуск, добавить её в раздел 6 `Backlog После MVP`.
5. Если идея меняет бизнес-процесс, сначала обновить `docs/07_decisions.md` и `docs/11_business_processes.md`, затем синхронизировать требования и техническое задание.

Формат оценки новой идеи:

```text
Идея:
Решает:
Решение по scope: MVP / post-MVP
Почему:
Куда добавлено:
```

## 8. Ближайший Следующий Шаг

Текущий следующий шаг: финальная фиксация MVP-коммита и решение о публикации/теге.

Причина: функциональные блоки M1-M5 закрыты, приёмочные проверки прошли, дальше нужны только действия релизного уровня.
