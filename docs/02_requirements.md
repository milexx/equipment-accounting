# Требования

Документ фиксирует финальные требования MVP на основе исходной постановки и рабочих проектных решений.

Бизнес-процессы подробно описаны в `docs/11_business_processes.md`.

## 1. Роли И Доступ

### Регион

Региональный пользователь:

- видит только оборудование своего региона;
- создаёт записи только в своём регионе;
- редактирует записи своего региона;
- прикладывает от 1 до 5 фото;
- отправляет записи на проверку в центр;
- видит замечания центра;
- не управляет типами оборудования;
- не видит фото и карточки чужих регионов.

### Центр

Пользователь центра:

- видит оборудование всех регионов;
- фильтрует список по региону, типу, статусу, базовым и динамическим полям;
- редактирует любую запись;
- принимает записи;
- классифицирует оборудование как рабочее, нерабочее или требующее диагностики;
- направляет оборудование на списание/утилизацию или оценку/продажу;
- возвращает записи на доработку;
- архивирует записи;
- управляет типами оборудования;
- управляет динамическими полями;
- выполняет экспорт.

### Пользователи MVP

В MVP допускается простая модель:

- один или несколько пользователей на регион;
- роль пользователя: `region`, `center` или `center_admin`;
- аутентификация через сессию или bearer token;
- модель должна позволять позже перейти на Keycloak.

Учётками регионов управляет центр. В промышленной модели это отдельная функция роли `center_admin`: создание пользователей, привязка к региону, блокировка и сброс пароля. Интеграция с Keycloak не входит в MVP и остаётся заглушкой через `AuthProvider`.

## 2. Жизненный Цикл Оборудования

Система учитывает не всё имущество организации, а оборудование, которое стало неиспользуемым.

Базовый целевой процесс:

```text
Неиспользуемое оборудование
        |
        v
Описание и подтверждение состояния
        |
        +--> Нерабочее -> списание -> утилизация
        |
        +--> Рабочее -> оценка -> продажа / магазин
```

Статусы:

- `draft` - черновик;
- `submitted` - отправлено регионом на проверку;
- `needs_revision` - центр вернул на доработку;
- `accepted` - принято центром;
- `diagnostics_required` - требуется диагностика;
- `writeoff_review` - готовится к списанию;
- `writeoff_approved` - списание согласовано;
- `disposal_pending` - ожидает утилизации;
- `disposed` - утилизировано;
- `valuation_pending` - требуется оценка;
- `valued` - оценено;
- `sale_ready` - готово к продаже;
- `listed_for_sale` - опубликовано для продажи;
- `sold` - продано;
- `archived` - архив;
- `deleted` - логически удалено.

Разрешённые переходы:

```text
draft -> submitted -> accepted
                 \-> needs_revision -> submitted
accepted -> diagnostics_required
accepted -> writeoff_review -> writeoff_approved -> disposal_pending -> disposed
accepted -> valuation_pending -> valued -> sale_ready -> listed_for_sale -> sold
accepted -> archived
any -> deleted
```

Физическое удаление записей в MVP не используется. Удаление реализуется через soft delete и статус `deleted`.

## 3. Оборудование

Обязательные базовые поля:

- ID;
- регион;
- тип оборудования;
- статус;
- наименование;
- дата создания;
- дата обновления;
- автор создания;
- автор последнего изменения.
- местонахождение.

Базовые необязательные поля:

- инвентарный номер;
- серийный номер;
- комментарий.
- состояние оборудования;
- описание поломки;
- комплектность;
- оценочная стоимость;
- цена продажи;
- описание для продажи.

Инвентарный и серийный номера не являются обязательными для всех типов, но должны быть доступны для фильтрации.

Местонахождение является базовым полем, потому что центр должен понимать, где физически находится оборудование: регион, площадка, склад, кабинет, стойка или иное описание.

Динамические поля хранятся в `attributes JSONB`, чтобы набор полей можно было менять через интерфейс без миграции БД и переписывания кода.

## 3.1. Состояние И Дальнейшая Судьба

Состояние оборудования:

- `unknown` - не подтверждено;
- `working` - рабочее;
- `broken` - нерабочее;
- `partially_working` - частично рабочее;
- `requires_diagnostics` - требуется диагностика.

Для MVP обязательны:

- `working`;
- `broken`;
- `requires_diagnostics`.

Если оборудование нерабочее, обязательны:

- описание поломки;
- минимум одно фото типа `defect`;
- комментарий или решение центра.

Если оборудование рабочее, оно может быть направлено на оценку и продажу.

Для продажи нужны поля:

- оценочная стоимость;
- цена продажи;
- описание для витрины/магазина;
- статус продажи;
- признак публикации.

## 4. Типы Оборудования

Центр может:

- создавать тип оборудования;
- переименовывать тип;
- включать/выключать тип;
- задавать набор полей для типа;
- менять порядок полей;
- выключать поле без удаления исторических данных.

Удаление типа, по которому уже есть записи, в MVP запрещено. Вместо этого используется `is_active=false`.

## 5. Динамические Поля

Типы полей MVP:

- `string` - строка;
- `text` - многострочный текст;
- `integer` - целое число;
- `decimal` - десятичное число;
- `date` - дата;
- `boolean` - да/нет;
- `select` - выбор одного значения;
- `multiselect` - выбор нескольких значений.

Настройки поля:

- код поля;
- название;
- тип значения;
- обязательность;
- порядок отображения;
- признак фильтрации;
- подсказка;
- правила валидации;
- варианты выбора для `select` и `multiselect`;
- активность.

Правила:

- код поля уникален внутри типа оборудования;
- код поля должен быть стабильным после начала использования;
- обязательность проверяется при отправке записи на проверку;
- условно обязательные поля в MVP не реализуются;
- поля с `is_filterable=true` должны иметь понятную стратегию индексации.

## 6. Фото

Требования:

- от 1 до 5 фото на единицу оборудования;
- максимум 10 МБ на файл при загрузке;
- форматы MVP: JPEG, PNG, WebP;
- первое фото считается главным;
- можно добавлять, удалять и менять порядок фото при редактировании;
- хранение оригиналов в файловой системе;
- хранение превью в файловой системе;
- в БД только метаданные и пути;
- генерация миниатюр на сервере при загрузке;
- доступ к оригиналам и превью только через авторизованный endpoint;
- регион не может получить фото чужого оборудования;
- логика фото изолирована в `PhotoStorage`.
- фото имеют назначение: общий вид, серийный номер, дефект, комплектность, прочее.

Пути:

```text
photos/ab/cd/uuid.ext
thumbs/ab/cd/uuid.webp
```

HEIC не входит в MVP.

Для нерабочего оборудования минимум одно фото должно иметь назначение `defect`.

## 7. Фильтрация И Списки

Список оборудования должен поддерживать:

- фильтр по региону;
- фильтр по типу оборудования;
- фильтр по статусу;
- фильтр по инвентарному номеру;
- фильтр по серийному номеру;
- фильтр по местонахождению;
- фильтр по состоянию;
- фильтр по дальнейшей судьбе: списание, утилизация, оценка, продажа;
- фильтр по статусу продажи;
- фильтры по динамическим полям с `is_filterable=true`;
- пагинацию;
- сортировку по дате создания/обновления.

По умолчанию регион видит только свои записи. Центр видит все записи.

## 8. Экспорт

Основной формат MVP - XLSX.

## 9. Одновременная Работа И Конфликты

Система должна поддерживать одновременную работу не менее 60 региональных пользователей, исходя из количества регионов, и активную параллельную работу пользователей центра.

Обязательные требования:

- пользователи разных регионов не должны блокировать друг друга при создании и редактировании своих записей;
- работа центра со списками, фильтрами и карточками не должна мешать регионам заводить оборудование;
- повторная отправка одной формы не должна создавать дубли;
- при одновременном изменении одной карточки система должна обнаруживать конфликт и не должна молча перетирать более свежие данные;
- смена статуса должна выполняться атомарно и только из актуального состояния;
- долгие операции, включая экспорт и обработку большого объёма фото, не должны держать транзакции БД дольше необходимого;
- все конфликтные изменения должны быть понятны пользователю через сообщение в интерфейсе.

Целевой подход:

- короткие транзакции на запись;
- optimistic locking для редактирования карточек;
- row-level lock только для критических операций смены статуса;
- идемпотентность создания и отправки форм;
- пагинация и лимиты для всех списков центра;
- audit log для разбора спорных изменений.

CSV допустим как дополнительный формат, если не увеличивает сроки.

Экспорт:

- учитывает текущие фильтры;
- включает базовые поля;
- включает динамические поля;
- включает идентификаторы/ссылки на фото, но не сами файлы;
- ограничен 10 000 записей для синхронного режима.

Если синхронный экспорт не укладывается в 10 секунд, он должен быть переведён в асинхронный режим.

## 9. Audit Log

Журналировать:

- создание записи;
- изменение базовых полей;
- изменение динамических полей;
- добавление фото;
- удаление фото;
- изменение порядка фото;
- изменение состояния оборудования;
- изменение решения о списании/утилизации/продаже;
- изменение оценки и цены продажи;
- смену статуса;
- архивирование;
- логическое удаление.

Каждая запись аудита содержит:

- ID оборудования;
- пользователя;
- регион пользователя;
- действие;
- старые значения;
- новые значения;
- дату и время.

## 10. Производительность

Ориентиры:

- до 500 000 записей оборудования;
- до 2.5 млн файлов фото;
- список с двумя фильтрами и пагинацией 50 записей - до 1 секунды;
- добавление/редактирование одной записи - до 0.5 секунды без учёта обработки больших фото;
- экспорт до 10 000 записей - до 10 секунд или асинхронно;
- пагинация обязательна;
- не отдавать более 500 записей без явного ограничения;
- запрещены запросы полного сканирования без `WHERE` и `LIMIT`.

## 11. Индексы

Обязательные индексы:

- `equipment.region_id`;
- `equipment.status`;
- `equipment.equipment_type_id`;
- `equipment.inventory_number`;
- `equipment.serial_number`;
- `equipment.location`;
- `equipment.condition`;
- `equipment.disposition`;
- `equipment.sale_status`;
- составные индексы для частых сценариев списка;
- GIN-индекс по `attributes`;
- expression-индексы по часто фильтруемым JSONB-полям.

## 12. Эксплуатационные Требования

MVP может быть развёрнут на одной VM или сервере:

- приложение;
- PostgreSQL;
- файловый каталог фото на отдельном диске/томе.

Backup должен включать БД и каталог фото как согласованный комплект.

Логи приложения должны позволять расследовать:

- ошибки авторизации;
- ошибки загрузки фото;
- ошибки генерации превью;
- медленные запросы;
- ошибки экспорта.

## 13. Требования К Интерфейсу

Интерфейс должен быть понятен без обучения.

Для регионов главный критерий - скорость и простота ввода:

- один основной сценарий `Добавить оборудование`;
- короткая форма-мастер;
- динамические поля появляются только после выбора типа;
- минимум административных элементов;
- понятные ошибки рядом с полями;
- загрузка нескольких фото сразу;
- сохранение черновика;
- возможность быстро добавить ещё одну запись такого же типа.
- отдельный простой выбор состояния: рабочее, нерабочее, нужна диагностика;
- если выбрано нерабочее, интерфейс сразу просит описать поломку и добавить фото дефекта.

Для центра главный критерий - управление большим объёмом данных:

- главный экран центра - реестр оборудования;
- быстрые фильтры по региону, типу и статусу;
- расширенные фильтры по динамическим полям;
- настройка колонок;
- сохранённые представления;
- массовые действия;
- экспорт из текущего набора фильтров;
- карточка оборудования с историей изменений.
- рабочие очереди: на проверке, требуется диагностика, к списанию, к утилизации, на оценку, готово к продаже, опубликовано, продано.

Подробная UX-спецификация находится в `docs/08_interface_ux.md`.
