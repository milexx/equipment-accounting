# Анализ Блокировки Avito И Успеха Duff89

Дата: 2026-06-22

## Вопрос

Почему основной обработчик `avito` может получить `HTTP 403`, а следующий за ним резервный `avito_duff89` успешно получает данные по тому же поисковому URL Avito?

## Наблюдаемые Факты

Запуск: `20260622T040909Z`

- `kyocera_m2040dn`: основной Avito вернул `HTTP 403` / `access_restricted_ip`.
- `kyocera_m2040dn`: Duff89/parser_avito сразу получил и сохранил 50 объявлений.
- `dell_r740`: основной Avito вернул `HTTP 403` / `access_restricted_ip`.
- `dell_r740`: результат Duff89/parser_avito существовал и был восстановлен из XLSX.
- `lenovo_t14`: основной Avito вернул `HTTP 200` и сохранил обычный снимок.

Это означает, что IP не был глобально заблокирован для всего трафика Avito во время run.

Метаданные ответа:

- заблокированные ответы основного обработчика пришли от `server: QRATOR`;
- заблокированные ответы основного обработчика выставили только ограниченные служебные/антибот cookies;
- успешный ответ Avito выставил более полный набор session-like cookies и содержал обычные SSR-признаки.

## Конфигурация Duff89 В Этом Запуске

Duff89 использовался без:

- прокси;
- собственных cookies;
- браузерного драйвера;
- API обхода;
- парсинга телефонов.

Значит успех `avito_duff89` не был связан с ротацией прокси, повторным использованием cookies, обходом CAPTCHA или браузерной автоматизацией.

## Наиболее Вероятное Объяснение

`avito` и `avito_duff89` — это два разных HTTP-клиента, которые обращаются к одному домену Avito.

Avito/QRATOR, судя по результатам, принимает решение о риске на уровне конкретного запроса по сочетанию факторов:

- репутация IP в этот момент;
- TLS-отпечаток и имитация браузера;
- сочетание user-agent и HTTP-заголовков;
- URL, категория и поисковая строка;
- недавняя последовательность запросов;
- cookies, выданные или не выданные в текущем запросе.

Основной обработчик и Duff89 оба используют `curl_cffi`, но каждый запрос выбирает свою имитацию браузера и свою сессию. Поэтому один запрос может быть заблокирован, а следующий соседний запрос другим клиентом может быть принят. Результат Day 5 нужно трактовать как блокировку на уровне запроса, а не как стабильный статус всего источника.

## Практический Вывод

Не записывать `blocked` основного Avito как итоговую оценку, если Duff89 вернул пригодные объявления.

Правильная семантика:

- `blocked` основного Avito — это данные о состоянии источника;
- успех Duff89 — итоговый источник цены для этой позиции;
- сохраненный снимок должен иметь `source: avito_duff89`.

## Добавленная Диагностика

Основной обработчик теперь пишет метаданные отпечатка запроса в `response_meta.json` для будущих запусков:

```json
{
  "request": {
    "impersonate": "chrome|edge|firefox|safari",
    "headers": {
      "user-agent": "..."
    }
  }
}
```

Это позволит в следующем запуске сравнить заблокированные и успешные запросы основного обработчика без повторного запуска только ради диагностики.

## Следующая Проверка

В следующем контролируемом запуске сравнить по каждой позиции:

- `response_meta.request.impersonate` основного обработчика;
- `response_meta.request.headers.user-agent` основного обработчика;
- HTTP-статус основного обработчика и cookies QRATOR;
- `good_request_count` / `bad_request_count` у Duff89;
- итоговый источник и медиану.

Если блокировки начнут коррелировать с конкретными значениями `impersonate` или несоответствием UA/отпечатка, основной обработчик можно будет сделать менее случайным и ближе к профилю клиента, который уже дает успешный результат.

## Проверка 2026-06-24

Запуск: `20260624T052753Z`

Наблюдение:

| Позиция | Primary Avito | Primary fingerprint | Итоговый источник | Duff89 result |
| --- | --- | --- | --- | --- |
| `kyocera_m2040dn` | `HTTP 200` | `impersonate=safari`, `Chrome/142` UA | `avito` | не запускался как итоговый fallback |
| `lenovo_t14` | `HTTP 403` | `impersonate=chrome`, `Chrome/143` UA | `avito_duff89` | `status=success`, `good_request_count=1`, `listings_count=48` |
| `dell_r740` | `HTTP 403` | `impersonate=chrome`, `Chrome/143` UA | `avito_duff89` | `status=success`, `good_request_count=1`, `listings_count=50` |

Дополнительные признаки:

- все ответы пришли от `server: QRATOR`;
- успешный primary Avito по Kyocera вернул обычные SSR-признаки, включая `x-ssr-request: 1`, и более полный набор cookies;
- заблокированные primary-ответы по Lenovo и Dell вернули только ограниченный набор QRATOR/anti-bot cookies;
- оба заблокированных primary-запроса были выполнены с одинаковым профилем `impersonate=chrome` и похожим UA `Chrome/143`;
- успешный primary-запрос Kyocera был выполнен с `impersonate=safari`, но UA при этом тоже Chrome-like, поэтому это пока не доказанная причинная связь.

Вывод по запуску 2026-06-24:

- это не проблема фильтров релевантности: primary Avito не дошел до получения объявлений по Lenovo и Dell;
- это не `no_data` и не ошибка нормализации: статус primary был `blocked`, `primary_http_status=403`;
- это не глобальная блокировка IP на весь run: Kyocera за несколько секунд до этого получила `HTTP 200`, а Duff89 затем получил объявления по обоим заблокированным URL;
- наиболее вероятно, QRATOR/Avito оценил риск на уровне конкретного HTTP-запроса или короткой последовательности запросов.

Практическое следствие:

- источник `avito_duff89` в дневной истории нужно трактовать как валидный fallback-снимок, а не как ухудшение качества ценовой точки само по себе;
- одновременно доля fallback-точек является метрикой нестабильности primary Avito и должна учитываться в решении о production-автоматизации;
- текущий режим `manual controlled run`, `one live run per UTC day`, `no retry loop after 403` остается правильным.

Рекомендация к следующему run:

- не делать повторный запуск 2026-06-24;
- в следующем UTC-дне сохранить те же позиции и порядок, чтобы проверить повторяемость;
- отдельно сравнить `impersonate`, UA, QRATOR cookies и `x-ssr-request` по successful/blocked primary-ответам;
- если `impersonate=chrome` продолжит коррелировать с `403`, убрать случайный выбор профиля из primary обработчика и сделать контролируемый A/B только в offline/debug режиме, не в боевом дневном запуске.

## Исправление 2026-06-24

Случайность в primary-запросе убрана в коде `worker.py`:

- `impersonate` теперь берется из `AVITO_PRIMARY_IMPERSONATE` или по умолчанию фиксируется как `safari`;
- `user-agent` теперь выбирается детерминированно из профиля либо задается через `AVITO_PRIMARY_USER_AGENT`;
- `random.choice` и `random.randint` больше не участвуют в primary-запросе.

Это значит, что следующий live run сравнит уже не рандомизацию, а один фиксированный профиль primary-запроса с тем же fallback `Duff89/parser_avito`.
