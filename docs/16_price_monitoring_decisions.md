# Проектные Решения По Модулю Мониторинга Цен

Документ фиксирует рабочие решения для будущего post-MVP модуля "Оценщик". Решения не меняют текущий MVP учёта оборудования и нужны для подготовки разработки отдельного модуля.

Связанные документы:

- `docs/14_price_monitoring_module.md` - ТЗ и архитектура;
- `docs/15_price_monitoring_mvp_plan.md` - план MVP модуля.

## Статус Модуля

Модуль мониторинга цен является отдельным post-MVP контуром.

Решения:

- не менять текущие сценарии учёта оборудования;
- не добавлять обязательные поля в карточку оборудования на первом этапе;
- не менять статусы текущего MVP;
- не рассчитывать цену продажи автоматически;
- проектировать модуль так, чтобы позже его можно было связать с карточкой оборудования.

## Цель Первого Релиза

Первый релиз должен дать оценщику проверяемую историю рыночных цен.

Решения:

- главная ценность первого релиза - регулярная история, а не мгновенная автоматическая оценка;
- система должна сохранять и дневные агрегаты, и объявления, на которых основан расчёт;
- оценщик должен видеть источник данных и иметь возможность проверить ссылку на объявление;
- отчёт должен показывать не только минимум и максимум, но и медиану.

## Владелец Процесса

До отдельного организационного решения владельцем процесса считается центр.

Решения:

- центр отвечает за принятие решений по цене продажи;
- администратор центра или назначенный оценщик управляет позициями мониторинга;
- региональные пользователи не управляют мониторингом цен;
- доступ регионов к дашборду оценщика в первом релизе не требуется.

Открытое решение перед разработкой:

- назначить конкретную роль владельца: `center`, `center_admin` или новая роль `valuer`.

## Роли

Для первого релиза использовать минимальное расширение прав.

Решения:

- просмотр дашбордов доступен центру;
- управление позициями доступно администратору центра;
- ручной запуск сбора доступен администратору центра;
- журнал ошибок доступен администратору центра;
- отдельную роль `valuer` не вводить, пока не подтверждена бизнес-потребность.

Задел:

- если оценщик станет отдельной функцией, добавить роль `valuer`;
- роль `valuer` сможет смотреть дашборды, управлять позициями и выгружать отчёты без доступа к admin-разделу текущего MVP.

## Пилотные Категории

Первый пилот должен включать несколько разных типов ликвидности.

Решения:

- не запускать модуль сразу на всём реестре;
- начать с 10-20 позиций;
- включить популярные и редкие позиции;
- использовать реальные модели из текущего реестра и демо-набора.

Рекомендуемый стартовый набор:

- МФУ;
- ноутбуки;
- серверы;
- мониторы;
- сетевое оборудование.

Примеры позиций:

- `Kyocera ECOSYS M2040dn`;
- `HP LaserJet Pro MFP M426`;
- `Lenovo ThinkPad T14`;
- `Dell PowerEdge R740`;
- `Dell P2419H`.

## География И Регион Поиска

В первом релизе позиция мониторинга должна уметь хранить регион поиска для внешней площадки. В контексте Avito это означает не регион пользователя системы и не регион владения оборудованием, а географический фильтр поиска объявлений на Avito.

Решения:

- у каждой позиции мониторинга есть поле `search_region`;
- значение по умолчанию - "Россия";
- "Россия" означает, что адаптер Avito выполняет поиск без ограничения одним городом или регионом, если площадка позволяет такой режим;
- если для позиции указан конкретный регион, например "Москва", "Санкт-Петербург" или "Новосибирская область", адаптер Avito должен преобразовать это значение в поддерживаемый Avito параметр или URL поиска;
- если площадка не поддерживает выбранный регион или регион не удалось однозначно сопоставить, система должна показать ошибку настройки позиции, а не молча искать по другому региону;
- в первом релизе отчёт строится по одному выбранному региону позиции, без сравнения регионов между собой;
- отдельные региональные срезы и сравнение регионов перенести после первого релиза.

Причина решения:

- для редкого оборудования локальный поиск часто будет давать пустые дни;
- федеральный поиск быстрее показывает общий рыночный диапазон;
- при продаже оборудования центр может использовать федеральный диапазон как ориентир, а логистику и региональную ликвидность учитывать вручную;
- поле `search_region` нужно заложить сразу, чтобы позже не менять модель данных.

Пример:

```text
Позиция: Kyocera ECOSYS M2040dn
search_region: Россия
AvitoParser: ищет объявления без ограничения одним городом или регионом.
Результат: дневной диапазон цен по общей выдаче Avito.

Позиция: Dell PowerEdge R740
search_region: Москва
AvitoParser: использует московский региональный фильтр Avito.
Результат: дневной диапазон цен по объявлениям из выбранной географии.
```

## Источники Данных

Первый целевой источник - Avito, если юридически и технически допустимо.

Решения:

- источник должен быть отдельной сущностью;
- логика конкретной площадки не должна попадать в отчёты и бизнес-сервисы;
- для Avito нужен отдельный адаптер;
- если нет явно доступного официального API для поиска рыночных объявлений, основной технический путь - исследовать HTML-парсинг Avito;
- разработку БД, UI и дашбордов не начинать до подтверждения, что источник данных можно реально заполнять.

Приоритет способов доступа:

1. официальный или партнёрский API, если он покрывает поиск чужих объявлений и цен;
2. HTML-парсинг Avito, если открытого API для такого поиска нет и парсинг допустим;
3. ручной или CSV-импорт только как временный fallback, но не как целевой механизм модуля.

Ключевое решение:

- источник данных является gate-условием проекта;
- если API не найден, нужно не строить пустой каркас, а сначала провести parsing discovery;
- результат discovery должен доказать, что можно получать минимум цену, ссылку, заголовок, регион и дату/время наблюдения.

## Ограничения По Avito

Модуль не должен проектироваться как инструмент обхода ограничений площадки.

Решения:

- не обходить CAPTCHA;
- не обходить авторизацию;
- не обходить rate limits;
- не использовать прокси как способ обхода запретов;
- соблюдать технические лимиты и задержки;
- фиксировать HTTP-ошибки;
- при массовых блокировках отключать источник или переводить запуск в ошибку;
- до промышленного запуска проверить актуальные правила площадки и `robots.txt`.

Блокирующее условие перед разработкой парсера:

- подтвердить допустимый и технически рабочий способ получения данных с Avito.

## Поисковый Запрос

В первом релизе у позиции один основной поисковый запрос.

Решения:

- поисковый запрос редактируется вручную;
- запрос не обязан полностью совпадать с названием позиции;
- бренд и модель хранятся отдельно, но для поиска используется поле `search_query`;
- несколько поисковых запросов на одну позицию не входят в первый релиз.

Задел:

- таблица `monitored_item_queries` может быть добавлена позже для альтернативных запросов.

## Состояние Оборудования

Состояние учитывать как параметр позиции, но не пытаться автоматически классифицировать объявления в первом релизе.

Решения:

- добавить ожидаемое состояние позиции;
- базовые значения: любое, рабочее, неисправное, на запчасти, новое;
- использовать состояние как подсказку для оценщика;
- автоматический разбор состояния из текста объявления перенести после первого релиза.

## Ценовые Показатели

Основной ориентир - медиана.

Решения:

- хранить минимум;
- хранить максимум;
- хранить среднюю;
- хранить медиану;
- хранить количество объявлений;
- показывать минимум и максимум как диапазон;
- использовать медиану как более устойчивый ориентир для цены.

Причина: минимум и максимум часто искажаются выбросами.

## Выбросы И Подозрительные Объявления

В первом релизе не удалять объявления из расчёта автоматически.

Решения:

- сохранять все распознанные объявления в рамках лимита;
- помечать подозрительные наблюдения флагами качества;
- не скрывать объявления от оценщика;
- ручное исключение из расчёта перенести после первого релиза.

Минимальные флаги:

- подозрительно низкая цена;
- подозрительно высокая цена;
- цена не распознана;
- возможный дубль;
- неполные данные объявления.

## Дни Без Данных

Отсутствие объявлений является бизнес-событием и должно храниться явно.

Решения:

- если сбор прошёл, но объявлений нет, писать дневной срез `no_data`;
- не оставлять пропуск в истории;
- показывать дни без данных на графике и в таблице;
- не считать `no_data` технической ошибкой.

## Ошибки Сбора

Технические ошибки отделяются от отсутствия данных.

Решения:

- если источник недоступен или парсер сломался, писать статус `failed`;
- если часть позиций обработана, запуск получает статус `partial_failed`;
- ошибка одной позиции не останавливает весь запуск;
- журнал ошибок обязателен в первом релизе;
- Telegram/email-уведомления перенести после первого релиза.

## Хранение Сырых Данных

В первом релизе не хранить полный HTML страниц.

Решения:

- хранить нормализованные поля объявления;
- хранить ссылку;
- хранить внешний идентификатор, если доступен;
- хранить технический `raw_payload_json` ограниченного размера;
- полный HTML не сохранять постоянно.

Причины:

- полный HTML увеличивает объём хранения;
- может содержать лишние данные;
- усложняет правила хранения и очистки.

## Экспорт

Первый формат экспорта - CSV.

Решения:

- CSV достаточен для первого релиза;
- Excel `.xlsx` перенести после первого релиза;
- экспорт должен учитывать выбранный период и фильтры;
- экспорт должен строиться по дневным срезам, а не по всем сырым объявлениям.

## Интерфейс

Интерфейс должен быть частью текущего server-rendered приложения.

Решения:

- использовать Jinja2;
- не делать SPA;
- графики строить простым клиентским графиком, например Chart.js;
- таблицы и формы делать в стиле текущего операционного интерфейса;
- основной раздел: `/pricing`;
- ручные действия должны быть доступны только пользователям с правом управления.

## Планировщик

Для первого релиза использовать встроенный планировщик.

Решения:

- APScheduler достаточен для 100-200 позиций;
- Celery и Redis не нужны в первом релизе;
- ежедневный запуск по умолчанию выполнять утром;
- ручной запуск нужен для диагностики и проверки запросов.

Задел:

- при росте выше 500 позиций или нескольких источниках перейти на очередь задач.

## Интеграция С Учётом Оборудования

Интеграция с карточкой оборудования не входит в первый релиз модуля.

Решения:

- первый релиз оценщика работает независимо;
- связь с карточкой оборудования добавить отдельным этапом;
- будущая связь должна быть ручной, а не автоматической;
- цена продажи в карточке не должна меняться без действия пользователя.

Будущий порядок:

1. запустить оценщик отдельно;
2. накопить историю;
3. проверить качество запросов;
4. добавить ручную связь карточки с позицией мониторинга;
5. показать рыночный диапазон в карточке;
6. дать центру использовать данные при заполнении цены продажи.

## Условия Старта Разработки

Перед началом разработки нужно закрыть:

1. владелец процесса мониторинга;
2. пилотные категории;
3. пилотный список 10-20 позиций;
4. допустимая и технически проверенная модель получения данных с Avito;
5. роли и права первого релиза;
6. подтверждение, что интеграция с карточками оборудования идёт отдельным этапом.

Если пункт про Avito не закрыт, разработку базовых компонентов модуля не начинать. Допустима только аналитика и технический spike по источнику данных.
