# Техническое Задание

## 1. Назначение Системы

Система предназначена для централизованного учёта оборудования в организации с головным подразделением и множеством удалённых регионов.

Система заменяет ручной Excel-процесс, снижает потери данных, ускоряет сбор информации и даёт центру единое место для контроля, фильтрации и выгрузки сведений.

## 2. Границы MVP

В MVP входит:

- веб-интерфейс для регионов и центра;
- учёт оборудования;
- разные типы оборудования с разными наборами полей;
- настройка типов и полей через интерфейс;
- обязательные фото оборудования;
- фильтрация и пагинация;
- экспорт;
- базовая авторизация;
- audit log;
- файловое хранение фото.

В MVP не входит:

- Keycloak, но архитектура должна быть готова к подключению;
- S3, но архитектура должна быть готова к переносу фото;
- импорт Excel;
- сложная аналитика;
- мобильное приложение;
- полнотекстовый поиск.

## 3. Роли И Права

### Регион

Региональный пользователь:

- видит только своё оборудование;
- создаёт записи только для своего региона;
- редактирует записи своего региона;
- прикладывает от 1 до 5 фото;
- отправляет записи на проверку в центр;
- видит замечания центра.

### Центр

Пользователь центра:

- видит оборудование всех регионов;
- фильтрует список по базовым и динамическим полям;
- редактирует любые записи;
- принимает записи;
- возвращает записи на доработку;
- архивирует записи;
- управляет типами оборудования;
- управляет динамическими полями;
- выполняет экспорт.

## 4. Жизненный Цикл Записи

Статусы:

- `draft` - черновик;
- `submitted` - отправлено регионом;
- `needs_revision` - требуется доработка;
- `accepted` - принято центром;
- `archived` - архив;
- `deleted` - логически удалено.

Переходы:

```text
draft -> submitted -> accepted
                 \-> needs_revision -> submitted
accepted -> archived
any -> deleted
```

Физическое удаление записей в MVP не используется. Удаление выполняется как soft delete.

## 5. Оборудование

Базовые поля:

- ID;
- регион;
- тип оборудования;
- статус;
- наименование;
- инвентарный номер;
- серийный номер;
- комментарий;
- динамические атрибуты;
- дата создания;
- дата обновления;
- автор создания;
- автор последнего изменения.

Инвентарный и серийный номера не являются обязательными для всех типов, но должны быть доступны для фильтрации.

## 6. Типы Оборудования И Динамические Поля

Центр может создавать и редактировать типы оборудования.

Для каждого типа задаётся набор динамических полей. Регион при выборе типа видит только поля этого типа.

Типы полей MVP:

- строка;
- многострочный текст;
- целое число;
- десятичное число;
- дата;
- булево;
- выбор из списка;
- множественный выбор.

Настройки поля:

- код;
- название;
- тип;
- обязательность;
- порядок отображения;
- подсказка;
- признак фильтрации;
- правила валидации;
- активность.

Динамические значения хранятся в `equipment.attributes JSONB`. Описание полей хранится в отдельной таблице.

## 7. Фото

Требования:

- минимум 1 и максимум 5 фото на единицу;
- максимум 10 МБ на файл;
- форматы: JPEG, PNG, WebP;
- хранение в файловой системе;
- в БД хранится путь и метаданные;
- превью генерируются на сервере;
- первое фото считается главным;
- доступ к фото только через авторизованный endpoint;
- регион не может получить фото чужого оборудования;
- при удалении записи фото удаляются по регламенту очистки или при окончательном удалении.

Пути должны использовать хэш-папки:

```text
photos/ab/cd/uuid.jpg
thumbs/ab/cd/uuid.webp
```

## 8. Производительность

Целевые параметры:

- до 500 000 записей оборудования;
- список с 2 фильтрами и пагинацией 50 записей - до 1 секунды;
- создание/редактирование одной записи - до 0.5 секунды;
- экспорт до 10 000 записей - до 10 секунд или асинхронно;
- не более 500 записей без пагинации;
- запрещены полные выборки без `WHERE` и `LIMIT`.

Обязательные индексы:

- `region_id`;
- `status`;
- `equipment_type_id`;
- составной индекс для частого списка;
- GIN по `attributes`;
- отдельные expression-индексы по часто фильтруемым JSONB-полям.

## 9. Архитектура

Стек:

- Python 3.11+;
- FastAPI;
- PostgreSQL 15+;
- SQLAlchemy 2.0;
- Alembic;
- Jinja2;
- HTMX;
- минимальный CSS;
- файловая система для фото.

Структура слоёв:

```text
api/            HTTP endpoints, формы, шаблоны
services/       бизнес-логика
repositories/   запросы к БД
models/         SQLAlchemy-модели
schemas/        Pydantic-схемы
auth/           AuthProvider
storage/        PhotoStorage
templates/      Jinja2
static/         CSS
```

Правила:

- `api/` не содержит SQL и не работает с файлами напрямую;
- `services/` не зависят от FastAPI;
- работа с фото идёт только через `PhotoStorage`;
- авторизация идёт только через `AuthProvider`.

## 10. Интеграционные Заделы

### Keycloak

Нужно создать интерфейс `AuthProvider`:

```python
class AuthProvider:
    def get_current_region_id(self, request) -> int | None: ...
    def has_permission(self, region_id: int | None, equipment_id: int) -> bool: ...
```

MVP-реализация:

- `DatabaseAuthProvider`.

Будущая реализация:

- `KeycloakAuthProvider`.

Переключение:

```text
AUTH_PROVIDER=database|keycloak
```

### S3

Нужно создать интерфейс `PhotoStorage`:

```python
class PhotoStorage:
    def save(self, file_data, equipment_id) -> list[str]: ...
    def delete(self, photo_ids) -> None: ...
    def get_url(self, photo_id) -> str: ...
    def get_thumbnail_url(self, photo_id) -> str: ...
```

MVP-реализация:

- `FilesystemPhotoStorage`.

Будущая реализация:

- `S3PhotoStorage`.

Переключение:

```text
PHOTO_STORAGE=filesystem|s3
```

## 11. Модель БД

Основные таблицы:

- `regions`;
- `users`;
- `equipment_types`;
- `equipment_type_fields`;
- `equipment`;
- `equipment_photos`;
- `equipment_audit_log`.

Ключевой принцип:

- базовые поля и поля доступа хранятся колонками;
- динамические поля хранятся в `attributes JSONB`;
- описание динамических полей хранится отдельно;
- часто фильтруемые динамические поля индексируются отдельно.

## 12. API И Страницы

Основные маршруты:

- `GET /equipment` - список;
- `GET /equipment/new` - форма создания;
- `POST /equipment` - создание;
- `GET /equipment/{id}` - карточка;
- `GET /equipment/{id}/edit` - форма редактирования;
- `POST /equipment/{id}` - сохранение;
- `POST /equipment/{id}/submit` - отправка на проверку;
- `POST /equipment/{id}/accept` - принятие центром;
- `POST /equipment/{id}/revision` - возврат на доработку;
- `POST /equipment/{id}/archive` - архивирование;
- `GET /equipment/{id}/photos/{photo_id}` - фото;
- `GET /equipment/{id}/photos/{photo_id}/thumb` - превью;
- `GET /equipment-types` - типы;
- `POST /equipment-types` - создание типа;
- `POST /equipment-types/{id}` - обновление типа;
- `POST /equipment-types/{id}/fields` - управление полями;
- `POST /exports/equipment` - экспорт.

## 13. Audit Log

Журналировать:

- создание записи;
- изменение базовых полей;
- изменение динамических полей;
- добавление/удаление фото;
- смену статуса;
- архивирование;
- удаление.

Запись аудита должна содержать:

- ID оборудования;
- пользователя/регион;
- действие;
- старые значения;
- новые значения;
- время.

## 14. Экспорт

Основной формат MVP - XLSX.

CSV допустим как дополнительный формат.

Экспорт должен учитывать текущие фильтры. Максимум синхронного экспорта - 10 000 записей. Если лимит времени не выполняется, экспорт переводится в асинхронный режим.

## 15. План Реализации MVP

1. Каркас приложения и миграции.
2. Регионы, пользователи, авторизация MVP.
3. Типы оборудования и динамические поля.
4. CRUD оборудования.
5. Фото и превью.
6. Модерация и статусы.
7. Фильтрация и пагинация.
8. Audit log.
9. Экспорт.
10. Нагрузочная проверка на тестовых данных.

## 16. Критерии Приёмки

MVP считается готовым, если:

- регион видит только свои записи;
- центр видит все записи;
- центр может создать новый тип и поле без миграции БД;
- регион видит динамическую форму по выбранному типу;
- запись нельзя отправить без фото;
- фото недоступны чужому региону;
- список работает с пагинацией;
- фильтр по региону, типу и статусу работает;
- фильтр по отмеченному динамическому полю работает;
- экспорт до 10 000 записей работает;
- все изменения попадают в audit log;
- есть инструкции по запуску и сопровождению.
