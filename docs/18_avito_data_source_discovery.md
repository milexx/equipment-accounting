# M0 Discovery Источника Данных Avito

Документ описывает обязательное исследование Avito как источника данных для модуля мониторинга цен. Без успешного M0 разработку БД, UI и дашбордов модуля не начинать.

Связанные документы:

- `docs/14_price_monitoring_module.md` - ТЗ и архитектура;
- `docs/15_price_monitoring_mvp_plan.md` - план MVP модуля;
- `docs/16_price_monitoring_decisions.md` - проектные решения;
- `docs/17_price_monitoring_developer_handoff.md` - handoff разработчику.

## 1. Цель M0

Цель M0 - доказать, что модуль мониторинга цен можно наполнять реальными данными с Avito.

Нужно получить ответ:

- есть ли официальный API, который подходит для поиска рыночных объявлений;
- если такого API нет, возможен ли технически и допустим ли организационно HTML-парсинг;
- какие данные реально можно получать стабильно;
- какие ограничения и риски есть до начала разработки модуля.

## 2. Главное Gate-Решение

M0 завершается одним из решений:

1. `go_api` - официальный или партнёрский API подходит, модуль можно проектировать вокруг API.
2. `go_parsing` - API не подходит, но HTML-парсинг технически работает и допустим к использованию.
3. `hold` - нужны дополнительные согласования с Avito, юристами или владельцем процесса.
4. `no_go` - надёжного и допустимого источника нет, разработку модуля в текущем виде не начинать.

Если результат `hold` или `no_go`, разработку M1-M6 не начинать.

## 3. Минимальный Набор Данных

Источник считается полезным, если по поисковому запросу можно получить минимум:

- цену;
- ссылку на объявление;
- заголовок объявления;
- регион или город объявления, если доступен;
- дату или относительное время объявления, если доступно;
- дату и время наблюдения;
- внешний идентификатор объявления, если доступен.

Дополнительно желательно:

- категория объявления;
- фото или признак наличия фото;
- продавец: частное лицо или компания, если доступно;
- состояние товара, если доступно;
- признак активности объявления.

Если цена и ссылка недоступны, источник не подходит для MVP модуля.

## 4. Проверка Официального API

### Что Проверить

На официальном портале разработчика Avito нужно выяснить:

- какие API доступны компании;
- есть ли API поиска объявлений по площадке;
- есть ли API поиска чужих объявлений, а не только управления своими объявлениями;
- можно ли искать по тексту;
- можно ли фильтровать по региону;
- можно ли фильтровать по категории;
- возвращается ли цена;
- возвращается ли ссылка на объявление;
- возвращается ли дата объявления;
- возвращается ли регион;
- есть ли лимиты запросов;
- есть ли ограничения по хранению полученных данных;
- можно ли использовать данные для внутренней аналитики цен;
- нужен ли платный тариф;
- нужен ли отдельный договор или партнёрский доступ.

### Где Смотреть

Основные точки:

- портал разработчика Avito;
- каталог API Avito;
- документация по авторизации;
- документация по объявлениям;
- условия использования API;
- условия использования Avito;
- поддержка Avito для профессиональных инструментов.

### Вопросы В Поддержку Avito

Если из документации неясно, нужно задать вопросы:

1. Есть ли API для поиска объявлений Avito по текстовому запросу?
2. Можно ли через API искать не свои объявления, а публичные объявления других продавцов?
3. Возвращает ли API цену, ссылку, город/регион и дату объявления?
4. Можно ли использовать API для внутреннего мониторинга рыночных цен?
5. Какие лимиты запросов действуют?
6. Нужен ли платный тариф или договор?
7. Можно ли хранить историю полученных цен внутри компании?
8. Есть ли ограничения на автоматический сбор цен по 100-200 позициям ежедневно?
9. Есть ли рекомендуемый официальный способ для такого сценария?

### API Go-Критерии

API подходит, если:

- доступен компании;
- разрешает сценарий внутреннего мониторинга цен;
- позволяет искать публичные объявления или получать релевантную выборку рынка;
- возвращает цену и ссылку;
- поддерживает текстовый запрос или эквивалентный механизм поиска;
- лимитов достаточно для 100-200 позиций в день;
- условия использования не запрещают хранить агрегированную историю.

API не подходит, если:

- доступен только для управления своими объявлениями;
- не возвращает публичную рыночную выдачу;
- запрещает хранение или аналитическое использование данных;
- лимиты не покрывают ежедневный мониторинг;
- доступ недоступен без отдельного длительного договора, который не планируется.

## 5. Parsing Spike

Parsing spike проводится только если нет явно подходящего API для поиска рыночных объявлений.

Цель spike - проверить техническую реализуемость HTML-парсинга Avito без разработки полноценного модуля.

### Что Проверить

Для 5-10 тестовых позиций:

- открывается ли поисковая выдача без авторизации;
- можно ли сформировать URL поиска по тексту;
- можно ли задать регион поиска;
- видны ли цены в HTML;
- видны ли ссылки на объявления;
- видны ли заголовки;
- есть ли внешний идентификатор объявления;
- есть ли признаки даты объявления;
- требуется ли JavaScript для получения данных;
- возникает ли CAPTCHA;
- возникают ли HTTP 403 или 429;
- насколько стабильно повторяются результаты;
- меняется ли структура HTML между запросами.

### Минимальный Прототип

Spike должен быть максимально маленьким.

Он может быть отдельным одноразовым скриптом вне основного приложения. Его задача - не заложить архитектуру, а доказать, что данные извлекаются.

Прототип должен:

- принять `search_query`;
- принять `search_region`;
- сделать один запрос;
- извлечь до 10 объявлений;
- вывести цену, ссылку, заголовок и регион;
- записать HTTP-статус;
- записать ошибку, если структура не распознана.

### Что Не Делать В Spike

Нельзя:

- обходить CAPTCHA;
- обходить авторизацию;
- применять агрессивные частые запросы;
- использовать прокси для обхода блокировок;
- встраивать spike в основной код;
- писать полноценные модели и UI до завершения M0.

## 6. Тестовые Позиции

Для M0 использовать 5-10 позиций из разных категорий и разной ликвидности.

Базовый набор:

```text
Kyocera ECOSYS M2040dn
HP LaserJet Pro MFP M426
Lenovo ThinkPad T14
Dell PowerEdge R740
Dell P2419H
Cisco Catalyst 2960
APC Smart-UPS 1500
HP ProDesk 400 G5
Canon i-SENSYS MF4410
Ubiquiti UniFi AP AC Lite
```

Для каждой позиции проверить:

- поиск с `search_region = Россия`;
- поиск с одним конкретным регионом, например `Москва`;
- количество найденных объявлений;
- качество совпадений;
- наличие цен;
- наличие ссылок.

## 7. Проверка Региона Avito

Нужно отдельно проверить, как Avito кодирует регион поиска.

Проверить:

- поиск без регионального ограничения;
- поиск по Москве;
- поиск по Санкт-Петербургу;
- поиск по одному региону не из столиц;
- что происходит при неизвестном регионе;
- можно ли получить список поддерживаемых регионов или его нужно вести вручную.

Результат должен ответить:

- как `search_region = Россия` преобразуется в Avito-запрос;
- как `search_region = Москва` преобразуется в Avito-запрос;
- что делать, если регион не сопоставлен;
- нужен ли справочник регионов Avito.

Решение по умолчанию:

- если регион не сопоставлен, показывать ошибку настройки позиции;
- не подменять регион автоматически;
- не искать молча по всей России вместо указанного региона.

## 8. Проверка Качества Данных

Для каждой тестовой позиции нужно оценить:

- релевантность первых 10-20 объявлений;
- долю объявлений с ценой;
- долю объявлений с нерелевантной моделью;
- наличие дублей;
- наличие подозрительно низких цен;
- наличие объявлений "на запчасти";
- наличие объявлений без фото, если это видно;
- достаточно ли выдачи для дневного среза.

Результат занести в таблицу:

```text
query
region
result_count
prices_found
links_found
relevant_count
irrelevant_count
captcha_seen
http_errors
notes
```

## 9. Проверка Нагрузки

Для MVP нужно до 100-200 позиций, но M0 не должен массово нагружать Avito.

В M0 проверить только:

- 5-10 позиций;
- не больше 1-2 регионов;
- малое число запросов;
- задержки между запросами.

После M0 оценить:

- сколько запросов понадобится в день;
- какую задержку нужно ставить;
- сколько времени займёт полный ежедневный сбор;
- какой лимит объявлений безопасен;
- нужна ли пауза между позициями.

## 10. Риски

### API Не Покрывает Сценарий

Вероятный риск: официальный API может быть ориентирован на управление своими объявлениями, сообщениями, статистикой или автозагрузкой, а не на поиск чужих объявлений.

Решение:

- переходить к parsing spike;
- не считать наличие API достаточным доказательством.

### CAPTCHA И Блокировки

Если CAPTCHA возникает уже на малом количестве запросов, HTML-парсинг может быть непригоден.

Решение:

- не обходить CAPTCHA;
- фиксировать `hold` или `no_go`;
- искать другой источник или официальный доступ.

### JS-Рендеринг

Если цены появляются только после JavaScript, простой `requests`-парсинг может не подойти.

Решение:

- оценить необходимость headless browser;
- отдельно оценить стабильность, нагрузку и допустимость;
- не включать Selenium/Playwright в MVP без отдельного решения.

### Низкая Релевантность

Поисковая выдача может содержать нерелевантные модели.

Решение:

- оставить ручной поисковый запрос;
- позже добавить фильтры по словам-исключениям;
- не делать автоматическую оценку цены без ручной проверки.

## 12. Go / No-Go

### Go API

Можно переходить к разработке модуля, если API:

- доступен;
- разрешает нужный сценарий;
- возвращает цены и ссылки;
- покрывает нужный объём;
- юридически допустим для внутренней аналитики.

### Go Parsing

Можно переходить к разработке модуля, если HTML-парсинг:

- стабильно извлекает цену и ссылку;
- работает без авторизации;
- не требует обхода CAPTCHA;
- не требует агрессивных запросов;
- допустим организационно;
- имеет понятные ограничения.

### Hold

Разработку не начинать, если:

- нужен ответ поддержки Avito;
- нужна юридическая проверка;
- нужно согласовать платный доступ;
- нужно решить, допустим ли headless browser.

### No-Go

Модуль в текущем виде не начинать, если:

- API не покрывает сценарий;
- HTML-парсинг нестабилен или недопустим;
- цены или ссылки недоступны;
- требуется обход CAPTCHA или авторизации;
- нет разрешённого источника данных.
