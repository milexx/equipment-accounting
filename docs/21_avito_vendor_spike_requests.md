# Vendor Spike По Источникам Данных Avito

Дата: 2026-06-17.

Статус: `fallback_vendor_track`.

Цель: резервный сценарий на случай, если self-service technical spike не даст рабочего источника данных.

Основной следующий шаг описан в `docs/22_avito_self_service_technical_spike.md`: сначала проверяются технические API/actors без общения с поставщиками.

Связанные документы:

- `docs/18_avito_data_source_discovery.md`;
- `docs/19_avito_data_source_discovery_results.md`;
- `docs/20_intermediary_avito_data_services.md`.

## 1. Контекст

Прямой официальный API Avito для поиска публичных объявлений по оборудованию не найден. Прямой HTML-запрос с сервера получил `HTTP 429` и CAPTCHA. Поэтому до разработки базы, UI и расписания нужно проверить внешний источник данных.

Этот документ не является обязательным планом общения с поставщиками. Он нужен как fallback, если технические self-service варианты не подтвердятся.

## 2. Кандидаты Для Первого Контакта

Основные кандидаты:

- MarketParser;
- ShopAPIS;
- Apify actor с поддержкой Avito, например `server0/avito-scraper`.

Резервный enterprise-кандидат:

- Bright Data Avito Scraper.

Не основной источник:

- Exa;
- SERP API.

Exa и SERP API можно использовать только для discovery и ручной проверки, но не для автоматического дневного среза цен.

## 3. Тестовый Набор Позиций

Для пилота используем 5 позиций разных типов, чтобы проверить качество поиска, шум и полноту:

| Код | Запрос | Тип | Регион | Лимит |
|---|---|---|---|---|
| T01 | `Kyocera ECOSYS M2040dn` | МФУ/принтер | Вся Россия | 50 |
| T02 | `HP LaserJet Pro MFP M426` | МФУ/принтер | Вся Россия | 50 |
| T03 | `Lenovo ThinkPad T14` | Ноутбук | Вся Россия | 50 |
| T04 | `Dell PowerEdge R740` | Сервер | Вся Россия | 50 |
| T05 | `Dell P2419H` | Монитор | Вся Россия | 50 |

`Вся Россия` в этом документе означает региональный фильтр Avito, а не географию нашей компании или оборудования.

## 4. Минимальный Набор Полей

Поставщик должен вернуть по каждому объявлению:

| Поле | Обязательно | Комментарий |
|---|---:|---|
| `source` | Да | Например `avito` |
| `external_id` | Желательно | ID объявления на стороне Avito или поставщика |
| `title` | Да | Заголовок объявления |
| `price` | Да | Цена числом, RUB |
| `currency` | Желательно | Обычно `RUB` |
| `url` | Да | Ссылка на объявление |
| `region` | Да | Регион/город объявления |
| `published_at` | Желательно | Дата публикации, если доступна |
| `updated_at` | Желательно | Дата обновления, если доступна |
| `fetched_at` | Да | Когда данные получены поставщиком |
| `seller_type` | Желательно | Частное лицо/компания, если доступно |
| `status` | Желательно | Активно/снято/неизвестно |
| `raw_payload` | Желательно | Исходный JSON для диагностики |

Минимально проходной вариант: `title`, `price`, `url`, `region`, `fetched_at`.

## 5. Текст Запроса Поставщику

Тема письма:

```text
Запрос пилота: данные Avito для мониторинга цен оборудования
```

Текст:

```text
Здравствуйте.

Мы проектируем внутренний сервис мониторинга рыночных цен на оборудование.
Нужен источник данных по публичным объявлениям Avito для ежедневного расчёта min/max/median цен по заданным позициям.

Просим подтвердить, можете ли вы предоставить данные по следующему сценарию:

1. Источник: Avito.ru.
2. География поиска: вся Россия как региональный фильтр Avito.
3. Количество позиций на старте: 100-200.
4. Частота сбора: 1 раз в день.
5. Лимит на одну позицию: 50-100 объявлений.
6. Формат доступа: API, webhook, регулярная JSON/CSV выгрузка или другой стабильный машинный формат.
7. Нужные поля: title, price, url, region/city, published_at или updated_at при наличии, fetched_at, seller_type при наличии, status при наличии.
8. История: желательно хранить или отдавать дневные срезы.
9. Требуется возможность задавать текстовый поисковый запрос по каждой позиции.

Для пилота просим выполнить или оценить 5 тестовых запросов:

- Kyocera ECOSYS M2040dn
- HP LaserJet Pro MFP M426
- Lenovo ThinkPad T14
- Dell PowerEdge R740
- Dell P2419H

По каждому запросу нужен пример 20-50 объявлений в JSON или CSV.

Также просим указать:

- стоимость для режима 100-200 позиций x 1 раз в день x 50-100 объявлений;
- есть ли SLA или гарантия доступности;
- что происходит при изменении структуры Avito;
- как обрабатываются CAPTCHA, блокировки и rate limits;
- есть ли ограничения по использованию данных;
- юридическую/compliance позицию по сбору публичных данных Avito;
- есть ли тестовый доступ или платный пилот на 1-2 недели.

Нам важно понять, подходит ли ваш сервис как стабильный источник данных для внутреннего аналитического инструмента, а не для массовой публикации или перепродажи данных.

Спасибо.
```

## 6. Дополнительные Вопросы Для Созвона

Задать всем поставщикам одинаковые вопросы:

1. Можно ли передавать произвольный поисковый запрос?
2. Можно ли явно указать регион Avito `вся Россия`?
3. Можно ли ограничить выдачу 50-100 объявлениями?
4. Возвращается ли цена именно числом?
5. Возвращается ли URL конкретного объявления?
6. Есть ли дата публикации или обновления объявления?
7. Можно ли отличить активное объявление от снятого?
8. Какой формат интеграции предпочтительный: API, webhook, файл, кабинет?
9. Есть ли расписание сбора на стороне поставщика?
10. Есть ли история выгрузок или нам нужно хранить историю самим?
11. Как поставщик решает CAPTCHA и блокировки?
12. Какие лимиты на запросы и объявления?
13. Что считается ошибкой сбора и как она отдаётся клиенту?
14. Есть ли retry, alerting, SLA?
15. Какие юридические ограничения на использование данных?

## 7. Формат Оценки Ответов

| Критерий | Вес | MarketParser | ShopAPIS | Apify | Bright Data |
|---|---:|---:|---:|---:|---:|
| Поддержка Avito search по тексту | 5 |  |  |  |  |
| Регион `вся Россия` | 5 |  |  |  |  |
| Цена числом | 5 |  |  |  |  |
| URL объявления | 5 |  |  |  |  |
| Дата/статус объявления | 3 |  |  |  |  |
| API или стабильная выгрузка | 5 |  |  |  |  |
| Расписание сбора | 4 |  |  |  |  |
| История/дневные срезы | 3 |  |  |  |  |
| Работа с CAPTCHA/блокировками на стороне поставщика | 5 |  |  |  |  |
| SLA/поддержка | 4 |  |  |  |  |
| Legal/compliance ясность | 5 |  |  |  |  |
| Стоимость подходит бюджету | 4 |  |  |  |  |
| Качество пилотных данных | 5 |  |  |  |  |

Оценка:

- `0` - нет или неизвестно;
- `1` - частично, высокий риск;
- `2` - работает, но есть ограничения;
- `3` - полностью подходит.

Решение принимается не по сумме баллов автоматически. Блокирующие критерии важнее общего score.

## 8. Блокирующие Критерии

Поставщик не подходит, если:

- не отдаёт цену числом;
- не отдаёт URL объявления;
- не поддерживает поиск по произвольному текстовому запросу;
- не поддерживает регион Avito или не может объяснить географию выдачи;
- не может вернуть хотя бы 50 объявлений по массовым категориям;
- не имеет API/выгрузки, пригодной для автоматизации;
- не даёт понятную позицию по ограничениям использования данных;
- требует, чтобы мы сами обходили CAPTCHA и блокировки.

## 9. Что Считать Успешным Пилотом

Пилот успешен, если по 5 тестовым позициям поставщик:

- возвращает структурированный JSON/CSV;
- по каждой позиции отдаёт релевантные объявления;
- цена заполнена минимум у 90% объявлений;
- URL открывается на конкретное объявление;
- регион заполнен минимум у 90% объявлений;
- дата публикации/обновления есть или поставщик честно фиксирует, что она недоступна;
- шум в выдаче приемлемый и может снижаться настройкой запроса;
- стоимость понятна для режима 100-200 позиций ежедневно;
- поставщик берёт на себя техническую сторону доступа к Avito.

## 10. Решение После Пилота

Варианты решения:

1. `go_vendor_provider` - выбран внешний поставщик, проектируем модуль вокруг provider API.
2. `go_apify_adapter` - выбран Apify actor как быстрый технический источник, но фиксируем повышенный риск поддержки.
3. `go_enterprise_provider` - нужен Bright Data или аналогичный enterprise-поставщик.
4. `hold_no_source` - ни один источник не подтверждён, разработку модуля не начинаем.
5. `direct_parser_research` - внешний источник не подходит, но бизнес готов отдельно обсуждать риски прямого парсинга.

Рекомендуемый проход:

1. Сначала запросить MarketParser и ShopAPIS.
2. Параллельно сделать тест Apify actor на 5 позициях, если доступен быстрый пробный запуск.
3. Bright Data подключать, если нужен SLA или первые два варианта не подходят.
4. Не проектировать таблицы и UI как обязательный следующий этап, пока не выбран источник данных.

## 11. Архитектурное Последствие

Будущий модуль должен проектироваться не вокруг конкретного парсера, а вокруг интерфейса поставщика данных:

```text
PriceDataProvider
  fetch_listings(query, region, limit) -> list[ExternalListing]
```

Возможные реализации:

- `MarketParserProvider`;
- `ShopApisProvider`;
- `ApifyAvitoProvider`;
- `BrightDataAvitoProvider`;
- `DirectAvitoParserProvider`.

Это позволит заменить поставщика без переписывания доменной модели, отчётов и UI.
