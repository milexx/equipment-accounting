# Проектные Решения

Документ фиксирует рабочие решения для первой версии ТЗ. Если бизнес-процесс уточнится, эти решения нужно обновить до начала разработки.

## Роли

В MVP используются две роли:

- `region` - региональный пользователь;
- `center` - пользователь центра.

Для простоты MVP допускает один технический токен/учётную запись на регион. При этом модель данных должна позволять добавить персональных пользователей позже.

Решение: заложить таблицу `users`, даже если в MVP она будет минимальной.

## Доступ

Регион:

- видит только записи своего региона;
- создаёт записи только в своём регионе;
- редактирует записи только своего региона;
- не управляет типами оборудования;
- не видит фото чужих записей.

Центр:

- видит все записи;
- редактирует все записи;
- управляет типами и полями;
- экспортирует данные.

## Статусы

Система ведёт оборудование, которое стало неиспользуемым. После проверки оно делится на нерабочее и рабочее.

Нерабочее оборудование идёт на списание и утилизацию. Рабочее оборудование идёт на оценку и продажу, в будущем может публиковаться в интерфейсе магазина.

Для MVP принять базовые статусы:

- `draft` - черновик;
- `submitted` - отправлено регионом;
- `needs_revision` - центр вернул на уточнение;
- `accepted` - принято центром;
- `archived` - архив;
- `deleted` - логически удалено.

Физическое удаление оборудования в MVP не используется. Удаление реализуется как soft delete / статус `deleted`.

## Модерация

В MVP нужна модерация центра.

Причина: исходный Excel-процесс страдает от ошибок и неполных данных. Если региональные записи сразу считать принятыми, центр снова получит грязные данные.

Базовый процесс:

```text
draft -> submitted -> accepted
                 \-> needs_revision -> submitted
accepted -> archived
any -> deleted
```

Целевой расширенный процесс:

```text
accepted -> diagnostics_required
accepted -> writeoff_review -> writeoff_approved -> disposal_pending -> disposed
accepted -> valuation_pending -> valued -> sale_ready -> listed_for_sale -> sold
```

## Базовые Поля Оборудования

Обязательные для всех типов:

- регион;
- тип оборудования;
- статус;
- наименование;
- инвентарный номер, если есть;
- серийный номер, если есть;
- комментарий;
- минимум одно фото.

Инвентарный и серийный номера не делать глобально обязательными, потому что у части оборудования их может не быть или они могут быть нечитабельны. Но их нужно поддержать как базовые поля для фильтрации.

## Динамические Поля

В MVP поддержать типы:

- `string`;
- `text`;
- `integer`;
- `decimal`;
- `date`;
- `boolean`;
- `select`;
- `multiselect`.

Поддержать настройки:

- обязательность;
- порядок отображения;
- подсказка;
- признак фильтрации;
- список вариантов для `select`/`multiselect`;
- минимальное/максимальное значение для чисел;
- минимальная/максимальная длина для строк.

Условно обязательные поля в MVP не делать. Это усложнит UI и валидацию.

## Фото

Разрешить форматы:

- JPEG;
- PNG;
- WebP.

HEIC не включать в MVP, так как он усложняет серверную обработку.

Для каждой записи:

- 1-5 фото;
- первое фото считается главным;
- можно добавлять, удалять и менять порядок фото при редактировании;
- оригинал хранить как загружен;
- превью генерировать на сервере;
- EXIF не использовать в бизнес-логике.

Для нерабочего оборудования фото является доказательством поломки. Минимум одно фото должно иметь назначение `defect`, а поле `defect_description` должно быть заполнено.

## Списание И Продажа

Новая целевая логика:

- все записи начинаются как неиспользуемое оборудование;
- центр подтверждает состояние;
- `broken` идёт на списание/утилизацию;
- `working` идёт на оценку/продажу;
- будущий магазин показывает только подготовленные к продаже позиции.

В MVP заложить поля оценки и продажи, даже если полноценный магазин будет реализован позже:

- оценочная стоимость;
- цена продажи;
- описание для продажи;
- статус продажи;
- признак публикации.

## Экспорт

MVP:

- XLSX как основной формат;
- CSV как дополнительный формат, если не увеличивает сроки.

Экспорт включает:

- базовые поля;
- динамические поля выбранного типа или всех типов;
- ссылки/идентификаторы фото, но не сами файлы.

Для объёма до 10 000 записей допустим синхронный экспорт, если укладывается в лимит. Если не укладывается - асинхронная задача.

## Импорт

Импорт из Excel не входит в MVP, но должен быть предусмотрен как следующий этап.

## Аудит

Audit log обязателен:

- создание;
- изменение;
- смена статуса;
- изменение фото;
- удаление/архивация;
- кто выполнил действие;
- когда;
- старые и новые значения.

## Эксплуатация

Для MVP допустимо развёртывание на одной VM или сервере:

- приложение;
- PostgreSQL;
- файловое хранилище фото на отдельном каталоге/томе.

Backup должен включать БД и каталог фото как согласованный комплект.
